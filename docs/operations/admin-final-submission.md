# 1R 최종 제출 점검의 어드민 통합

- 상태: **migration — 코드 통합, 운영 DB·API 반영은 별도 승인 대상**
- 기준일: **2026-11-24**

## 목적과 진입점

`/admin/growth/business-plan/?view=final-submission`은 모두의 창업 1R 제출 직전의 보완사항을
관리하는 개인 보드다. 웹 관리자 Growth 메뉴, 독립 관리자 메뉴, 통합 작업실의 사업 영역에서
진입한다. 기존 사업계획서 보드와 저장 범위가 분리되어 있다.

활동보고서·사업계획서·지출 증빙 대장의 관리 후보와 플랫폼 관찰 기록을 같은 화면에서
비교한다. 파일명·버전·원본 작성/수정일·근거 링크·첨부 증빙 참조·불일치·다음 조치·최종
확인자와 확인 시점을 기록하며, 다섯 상태를 사용한다.

| 상태 | 의미 |
| --- | --- |
| 미확인 | 파일 또는 플랫폼 사실을 확인할 근거가 부족함 |
| 검토 필요 | 확인해야 할 차이나 검토 요청이 남음 |
| 보완 중 | 점검 기록에 따라 보완을 진행하는 상태 |
| 승인 대기 | 실행 범위와 필요한 승인을 기록하는 상태 |
| 최종 확인 | 근거·확인자·시점이 있고 미해결 표시를 해제한 점검 결과 |

실제 제출·제출 파일 교체·외부 계정 접근·원본 문서 수정은 네 개의 고정 승인 대기 항목이다.
API와 화면에는 이 작업을 실행하는 기능이 없다. 기존 가격·출시 문구·인프라 증빙·교육자료의
규칙 분석을 다시 작성하는 대신 최종본에 반영되었는지와 제출을 막는 보완사항을 관리한다.

## 근거와 판정

- 보드 저장 시각은 원본 파일 작성일·수정일이나 플랫폼 제출 시각을 대신하지 않는다.
- 플랫폼 제출/미제출 판정에는 근거 URL과 관찰 시점이 필요하다. 근거가 없으면 미확인이다.
- 첨부 비교에는 양쪽 파일명, 관찰 근거, 시점과 비교 메모가 필요하다. SHA256이 서로 다르면
  일치 확인을 거절한다.
- 기준 파일 또는 플랫폼 첨부의 식별 정보가 바뀌면 기존 비교·확인 결과를 해제한다.
  기준 변경을 먼저 서버에 저장한 뒤 새로운 기준으로 최종 확인한다.
- 보고서와 증빙 대장 대조는 양쪽 파일 변경을 확인하며, 전체 플랫폼 접수 점검은 세 필수
  문서의 제출 여부와 첨부 비교를 함께 확인한다.
- 시간대가 없는 과거 관찰 시각은 시간대를 추측하지 않는다. 명시적인 시간대가 있는 시각만
  KST로 변환해서 표시한다.

## 기존 Sites 기록 가져오기

1. 기존 소유자 전용 Sites에서 전체 기록 JSON을 내보낸다.
2. 로그인한 관리자 계정에서 전용 화면의 **Sites JSON 가져오기**를 연다.
3. 원본 저장 버전·내보낸 시점·파일 목록·상태별 개수를 검토한다.
4. 필요한 현재 어드민 기록을 JSON으로 보관한 뒤 교체 확인을 선택한다.
5. 검토한 기록을 화면에 반영하고 **서버에 저장**한다.

첫 가져오기는 검증된 원본 확인 상태를 유지한다. 기존 어드민 기록을 교체할 때는 변경된
기준의 오래된 판정을 다시 검토하도록 해제한다. Sites revision은 어드민의 동시 저장 버전으로
사용하지 않는다. 원본 Sites와 JSON에 남은 과거 이력은 어드민에서 새로 발생한 감사 이력으로
위장하지 않으며, 어드민에는 가져오기 이후의 서버 저장 이력이 쌓인다.

이후 Sites와 어드민의 기록은 각각 저장된다. 자동 동기화, 기관 플랫폼 접속, 원본 파일의
업로드·수정은 수행하지 않는다. 개인 자료와 Sites 접근 토큰을 소스·정적 번들에 넣지 않는다.

## 저장과 권한 경계

공유 계약은 `packages/contracts/src/final-submission/`에 있고, 화면과 API가 같은 검증을 쓴다.
API는 `apps/api/src/modules/final-submission/`에 있다.

| API | 동작 |
| --- | --- |
| `GET /api/admin/final-submission` | 현재 세션의 개인 기록 조회. 최초 조회는 행을 만들지 않음 |
| `GET /api/admin/final-submission/export` | 현재 세션과 활성 역할을 다시 확인한 내보내기 |
| `POST /api/admin/final-submission/save` | 기준 revision·mutation ID·변경 요약·보드를 검증한 저장 |

활성 관리자·운영자가 본인 계정의 자료만 읽고 쓴다. 기존 사업계획서 보드의 공유 권한은
승계하지 않는다. 소유자 ID는 세션 principal에서 결정하며 클라이언트 주입을 거절한다.
클라이언트도 응답 소유자를 확인하고 계정 전환 전 응답을 버린다. 재인증 중에는 자료와
편집창을 숨기며, 권한이 거절되면 메모리의 기록·초안을 제거한다. 브라우저 저장소에 자료를
지속 저장하지 않는다.

개인 원장, 감사, 멱등 영수증을 같은 트랜잭션에 저장한다. 다른 창의 저장은 revision 충돌로
차단하고, 연결 중단으로 결과를 알 수 없을 때는 동일한 mutation으로 결과를 다시 확인한다.
입력 거절은 초안 보완을 허용한다. 감사 이력은 DB에 보존하고 화면에는 최신 100개를 반환한다.
DB가 준비되지 않았거나 저장본이 손상되면 503으로 실패하고 기본값으로 덮어쓰지 않는다.

## 운영 적용 순서와 승인 경계

신규 SQL은 `apps/api/src/platform/database/migrations/0134_admin_final_submission.sql`이다.
개인 원장·감사·영수증 세 테이블, 소유자 RLS, 최소 runtime ACL, 이력 보호를 추가한다.
기존 사업계획서 보드, 클라우드 작업 보드, Sites D1은 이 SQL의 대상이 아니다.

`AGENTS.md` 8절, `deploy/DEPLOY_MANIFEST.json`, `DEPLOY.md`에 따라 현재 onpod 운영 DB와
API 이미지 교체는 별도 명시 승인이 필요하다. 코드를 병합한 것만으로 운영 반영되었다고
보고하지 않는다. 승인 이후에도 현행 인프라 지도와 배포 절차를 먼저 확인한다.

1. 승인할 main SHA, 검증 결과, 대상 SQL, 직전 정상 이미지 SHA를 확정한다.
2. 실제 운영 DB의 적용 이력과 runtime 구성을 확인하고 신규 SQL의 적용 순서를 정한다.
   과거 다른 공급자용 migration workflow를 onpod에 그대로 실행하지 않는다.
3. 승인된 DB 변경을 적용하고 신규 세 테이블·인덱스·RLS·ACL을 확인한다.
4. 같은 승인 SHA의 불변 GHCR 이미지로 onpod API를 교체한다.
5. 승인 SHA와 산출물이 일치하는 정적 웹을 현행 Cloudflare 절차로 배포한다.
6. 원점 readiness, 관리자 인증, 다른 계정 격리, 개인 저장·재조회·내보내기를 확인한다.
   실제 기관 제출이나 원본 문서 수정은 이 검증에 포함하지 않는다.

복구는 직전 정상 API 이미지를 지정하는 현행 절차를 따른다. 추가 테이블과 감사 기록은
보존한다. `onpod app rollback`, 자동 스키마 변경, 이력 삭제로 복구하지 않는다.
