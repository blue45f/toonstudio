## 검증 환경과 범위

- 실제 앱 개발 서버 `http://127.0.0.1:5178`에 독립 `chromium.launch()`로 접속했다.
  사용자 브라우저와 CDP 연결을 공유하지 않았다.
- 모바일은 390×844 CSS px, 터치 지원, 한국어, reduced motion으로 검사했다.
  전체 메뉴의 PC 화면은 1440×900 CSS px에서 추가 확인했다.
- 새 guest 브라우저 문맥에서 검사했으며 실제 앱 순회에는 API 응답 대체나 프로젝트 fixture를 넣지 않았다.
- 본문 고유 h1과 라우트 준비 상태를 기다린 뒤 측정했다. 초기 지연 로딩의
  `data-route-semantic-heading`은 최종 페이지 제목으로 판정하지 않았다.
- 가로 넘침은 문서 `scrollWidth`와 viewport 폭으로 검사했다. 작은 조작 영역은
  첫 viewport의 기하 후보를 모은 뒤 부모 label, 닫힌 details, 문장 안 링크 여부를 구분했다.
  모든 패널·모든 스크롤 위치의 접근성 전수 검사 결과는 아니다.

첫 Tab은 모두 `본문으로 건너뛰기`에 도달했다.

로컬 API 프록시는 인증·카탈로그·마켓 등에서 502를 반환했다. 수집한 콘솔 오류는
해당 HTTP 리소스 실패였고, 이 순회에서 별도 JavaScript 예외는 발생하지 않았다.
화면의 `ready`는 UI가 준비됐다는 뜻이며 서버 데이터 조회 성공을 뜻하지 않는다.

작품 찾기·조건 탐색·랭킹·커뮤니티에서는 불러오기 실패와 재시도를 표시하는 것을 확인했다.
커뮤니티는 글을 불러오지 못한 상태를 “현재 글이 없다는 뜻은 아닙니다”로 구분했다.
연재 캘린더에서도 API 실패 안내와 재시도를 확인했다.
연결 안내의 초기 “온라인 기능을 연결하는 중”은 기존 90초 cold-start 정책 범위다.

실제 카탈로그의 유효 작품을 가져오지 못했으므로 추가 두 경로
`/title/mobile-qa-missing-title`, `/title/mobile-qa-missing-title/read/1`은 **조회 실패 경계만** 확인했다.
상세에는 재시도, 리더에는 재시도와 작품 상세 복귀가 표시됐다.
유효 작품 상세·회차 열람 성공이나 독자 데이터 저장을 검증한 결과가 아니다.

## 분리된 메뉴와 실제 이동

전체 메뉴는 모바일에서 일곱 목적을 1열로, PC에서 같은 목적을 2열로 제공한다.
작품 시작은 `/create`, 내 작업은 `/studio`로 연결하고 상세 기능 목록은 `/sitemap/all`에서만 연다.
모바일 하단은 내 작업·작품 찾기·소재 찾기·내 정보·전체 메뉴의 다섯 목적을 제공한다.

공통 푸터는 전체 메뉴·도움말·이용 정책을 먼저 보여주며, 나머지 기존 링크는
“서비스 안내 더 보기”를 열면 나타난다. 모바일과 PC에서 기본 접힘·펼침을 각각 캡처하고
펼친 상태에서도 가로 넘침 0px를 확인했다. 메뉴 선택 페이지에는 공통 창작 안내나 다음 작업 목록을 덧붙이지 않는다.

기존 브라우저 회귀를 새 구조에 맞춰 실행했다. 아래 네 테스트가 통과했다.
이 테스트들은 API 장애 fixture를 사용하므로 위의 실제 guest 순회와 구분한다.

| 테스트 | 확인한 결과 |
| --- | --- |
| `non-studio-controls.spec.ts`의 주행동 대비 | 메뉴 허브의 작품 시작과 전체 디렉터리의 기존 제보 링크를 포함한 대비 검사 통과 |
| `non-studio-experience.spec.ts`의 실제 클릭 순회 | 내 작업 → 메뉴의 자료·성장 → 리서치 → 작품 찾기 → 함께 보기 → 커뮤니티 → 갤러리 → 내 작업 이동 통과 |
| 같은 파일의 디렉터리 검색·Back·복구 | 허브에서 `/sitemap/all` 진입, 검색 조건 URL, 학습 기록 이동, Back 후 검색 복원, 빈 결과·초기화·초점 유지 통과 |
| `site-directory-health.spec.ts`의 지정 경로 검사 | 메뉴 허브·전체 디렉터리·일곱 목적 페이지의 총 9개 경로에서 제목·랜드마크·준비 상태·가로 넘침 검사 통과 |

마지막 검사는 `SITE_HEALTH_ROUTES`로 위 9개 경로를 지정한 실행이다.
전체 디렉터리의 수백 목적지를 전수 실행한 결과로 확대하지 않는다.

## 작은 조작 영역 수정과 재측정

실제 모바일 검사에서 발견한 두 조작 영역을 수정한 뒤 같은 폭에서 재측정했다.

| 조작 | 수정 전 | 수정 후 실측 |
| --- | --- | --- |
| 작품 찾기 검색 제출 | 43×48px | **48×48px** |
| 소재 마켓의 “펜선 ↗” 추천 검색어 | 35×44px | **44×44px** |

작품 찾기 입력도 최종 **272×44px**로 확인했다. 초기 입력의 내부 높이 후보는 전체
label 클릭 영역과 구분했고, 조건 탐색의 닫힌 안내 안 문장 링크는 기본 화면의 작은 버튼으로 세지 않았다.

## 실제 캔버스 생성 경로

별도 새 guest 문맥에서 `/create`의 “캔버스 열기”를 실제로 눌렀다.
기존 생성 함수가 로컬 프로젝트 1개와 문서 저장소 항목 1개를 만들었고,
정본 `/studio/p/:projectId/d/:documentId?workspace=draw...`로 이동했다.
`#studio-app-shell`과 모바일 그리기 UI가 표시됐으며 수집한 JavaScript 예외는 0개였다.
브라우저 문맥을 닫아 이 검증용 로컬 데이터를 사용자 브라우저에 남기지 않았다.

이 검사는 작업 생성과 에디터 진입까지만 확인한다. 실제 획의 저장·undo/redo·재열기·출력까지 통과했다는 의미는 아니다.
그 경계의 후속 회귀에는 다음 기존 테스트가 적합하다.

- `e2e/studio-pigment-product-workflow.spec.ts`의 V1/V2 원고 전환·undo/redo·재열기·내보내기:
  실제 앱의 내구 저장 결과와 출력 파일을 검사한다. 합성 원고로 시작하는 테스트임을 구분한다.
- `e2e/studio-data-persistence-browser.spec.ts`: 실제 브라우저 저장소를 쓰는 독립 합성 하네스다.
  전체 에디터의 실사용 순회와 같은 증거로 취급하지 않는다.
- `studio-full-verification.spec.ts`의 단순 포인터 smoke만으로 저장 성공을 보증하지 않는다.
