# 최신 아키텍처 기준 — 가독성, AI 분석 용이성, 분리·격리·확장성, 성능 (PR #2536 기준 문서)

> 이 문서는 PR #2536의 설계에 사용자가 추가한 기준을 명문화한다.
> 코드·설정 변경은 없다. 이 기준은 이후 변경을 판단하는 잣대이지, 이미 95점을 달성했다는 주장이 아니다.

## 1. 요점 — 사람이든 다른 AI든, 처음 보는 사람이 10분 안에 구조를 파악할 수 있어야 한다

- 폴더 이름이 곧 종류이다: `apps/`는 실행 단위, `packages/`는 재사용 단위, `services/`는 별도 배포 단위,
  `crates/`는 엔진, `docs/`는 문서, `tests/`·`e2e/`·`scripts/verify-*`는 검증 층이다.
  같은 종류가 두 곳에 있으면, 그 자체가 부채이다.
- 파일 이름이 곧 역할이다: `*-contract`, `*-registry`, `*-ledger`, `*-ratchet` 같은 접미사는
  그 파일이 무엇을 보장하는지 말해야 한다. 이름만 보고 내용을 유추할 수 없으면 이름을 바꾼다.
- 한 파일은 한 책임이다: 1,000개가 넘는 메가 도메인, 250KB급 검증 스크립트, 60KB급 원장은
  그 자체로 가독성과 분석의 적이다. 쪼갤 때는 폴더를 나누는 것이 아니라,
  공개 export와 경계 규칙을 먼저 정하고 그 다음에 나눈다.

## 2. AI 분석 용이성 — AI가 추론하지 않고 읽을 수 있게 만든다

- 정본은 하나이다: 루트 `AGENTS.md`가 정본이고, 다른 에이전트 지침은 복제가 아니라 참조이다.
  `docs/README.md`의 권위 순서(소스·테스트 > 원장·ratchet > 아키텍처 > ADR > 역사·벤치마크 > OpenWiki)를 깨지 않는다.
- 인덱스가 곧 지도이다: `deploy/README.md`, `config/README.md`, `docs/apps-packages-map-*`,
  `docs/tests-docs-ci-map-*`처럼, 목록이 곧 탐색 경로가 되어야 한다.
  인덱스 없이 256개 문서를 뒤지는 구조는 AI에게도 사람에게도 분석이 아니다.
- 상태는 파일 안에 적는다: 문서 첫머리에 `current` / `migration` / `target` / `legacy exception` 중 하나를 적는다.
  날짜가 없는 계획, 구현되지 않은 계획을 현재 기능처럼 쓰지 않는다.
- 히스토리는 히스토리 자리에만 둔다: 날짜형 보고서·벤치마크·증거는 현재 구조 문서와 섞지 않는다.
  현재 문서를 읽을 때 과거 보고서가 끼어들면, AI는 과거를 현재로 오인한다.
  그래서 히스토리 파일은 참조 0건이고 주제가 종료된 것부터 과감히 제거하고, 나머지는 날짜 폴더로 모은다.

## 3. 기능 분리·격리 — 바꾸면 그 범위 안에서만 깨진다

- 의존 방향은 한 방향이다: `apps → packages → core`, 역방향 금지, 도메인 간에는 공개 export로만 통한다.
- 경계는 문서가 아니라 기계가 지킨다: `config/architecture-boundary-ratchet.json`,
  `config/architecture-source-ratchet.json`, `scripts/validate-app-boundaries.mjs`가 이미 있는 것처럼,
  경계 규칙은 테스트·ratchet으로 강제한다. 문서에만 적힌 경계는 경계가 아니다.
- 격리의 단위는 배포 단위와 같다: 현재 유일하게 올바른 분리는 GPU 추론 서비스뿐이다.
  나머지를 마이크로서비스로 쪼개는 것은 솔로 팀에서 격리가 아니라 운영 부채이다.
- 실패도 격리한다: 한 엔진(Skia/ThorVG/Vello/Hokusai)이 깨져도 다른 엔진 경로가 깨지지 않도록,
  레지스트리·역할 원장 패턴을 유지한다. 자동 폴백은 금지한다(ADR-0018).

## 4. 확장성 — 새 것을 추가할 때 기존 것을 고치지 않는다

- 새 도메인·패키지·엔진은 기존 도메인을 편집하지 않고 추가한다: 레지스트리에 등록하고, 공개 export를 추가하고, 경계 테스트를 추가한다.
- `packages/core` 같은 god 패키지는 확장성의 적이다: 한 `index.ts` 뒤에 상거래·지갑·음악·분류가 다 있으면,
  새 기능이 기존 기능을 건드린다. 쪼갤 때는 re-export를 먼저 두고, 소비자를 한 번에 바꾸지 않는다.
- 설정도 확장 가능하게: 설정 파일은 루트에 두어야 하는 도구는 루트에 두되, 종류별 인덱스와 공유 베이스로 묶는다.
  설정 파일을 폴더로 물리 이동해서 도구가 못 찾게 만드는 것은 확장이 아니다.

## 5. 성능 — 빠른 피드백이 곧 성능이다

- 테스트가 빌드를 기다리지 않는다: `test:fast`(빌드 없음)와 `test:full`을 분리하는 것이
  가장 큰 피드백 성능 개선이다. 빌드·타입체크·테스트를 한 명령에 묶어두면, 작은 수정도 전체를 기다린다.
- 번들은 손으로 튜닝한 만큼 깨지기 쉽다: `vite-manual-chunks`를 바꿀 때는 반드시 `check:studio-bundle` ratchet으로 검증한다.
- 메모리 상한을 낮추는 것은 최적화가 아니다: tsc·vite·lint의 높은 메모리 상한은 그래프가 크기 때문이다.
  그래프를 쪼개기 전에 상한을 낮추면 빌드가 터진다.
- 큰 JSON·큰 패치·큰 벤더 엔진은 로더를 먼저 본다: 파일을 쪼개는 것이 아니라,
  누가 언제 그 파일을 읽는지부터 확인한다. 읽지 않는 파일을 쪼개는 것은 성능 개선이 아니다.

## 6. 이 기준을 어떻게 적용하는가 (체크리스트)

1. 새 파일·폴더를 만들 때: 종류가 분명한가, 이름이 역할을 말하는가, 공개 export가 정해졌는가.
2. 문서를 만들 때: 정본인가, 인덱스에 들어가는가, 상태(`current` 등)가 첫머리에 있는가, 히스토리와 섞이지 않았는가.
3. 삭제할 때: 참조 0건 + 주제 종료 + 대체 문서 존재(또는 대체 불필요) 중 최소 두 가지를 만족하는가.
4. 성능을 말할 때: 측정 조건·대상·전후 수치가 있는가. 숫자가 없으면 주장하지 않는다.
5. AI가 분석할 때: 이 문서와 인덱스만으로 구조·경계·정본을 찾을 수 있는가. 찾을 수 없으면 구조가 아직 미완이다.
