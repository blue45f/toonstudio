# 프로젝트별 직군 권한과 인계·승인 잠금

상태: **migration** — 2026-11-04 사용자 승인에 따라 구현한 선택 적용 기능이다. 기존 프로젝트의
기본값은 OFF이며, 이 문서만으로 운영 배포나 운영 프로젝트 활성화를 완료한 것으로 판단하지 않는다.

## 적용 범위

개인 직군 프로필과 분업 계획 화면은 화면 정렬·추천·체험 용도다. 실제 권한은 제작 프로젝트의
관리자가 이 기능을 켜고 실제 계정의 제작 배정, 등록된 원고 범위, 공정별 작업을 연결해야 생긴다.

기존 owner/admin/editor의 전체 편집 ACL, viewer/commenter의 독립 제한 편집 grant를 유지한다.
기능을 켠 프로젝트에서는 명시적으로 매핑한 대상에만 추가 검사를 적용한다. 소유자·관리자·전체
편집자도 현재 역할 배정 없이 다른 담당 범위나 인계·승인된 범위를 수정할 수 없다. 매핑 밖의
일반 편집·제목·표지·설정 기능은 기존 ACL을 유지한다. 보호 대상에 영향을 주는 전역 크기·프레임·
레이어·공유 픽셀 surface 변경과 렌더 의존성은 같은 효과 검사로 판정한다.

## 관리자의 설정 순서

1. 제작 프로젝트의 **설정** 화면에서 **실제 원고의 담당 편집 범위 배정**을 연다.
2. 기존 담당 범위 등록 기능으로 저장 원고의 실제 페이지·컷·레이어·요소를 불변 캡처와 대조해
   등록한다. 폴더 이름이나 직군 프로필로 원고 귀속을 자동 추정하지 않는다.
3. **프로젝트 직군별 원고 보호**에서 15직군을 현재 작품에 참여 중인 실제 계정의 제작 배정에
   연결한다. 같은 직군에 여러 배정을 선택할 수 있고 총괄 1인작가도 명시적으로 배정해야 한다.
4. 18종 제작 레이어 그룹을 실제 등록 범위에 연결한다. 하나의 대상은 한 그룹에만 연결하고,
   서로 겹치는 페이지·컷·레이어 보호 범위를 중복 연결하지 않는다.
5. 여덟 공정에 서로 다른 실제 제작 작업을 연결하고 전체 편집자에게도 적용됨을 확인한 뒤
   **이 프로젝트의 원고 보호 켜기**를 누른다.

서버는 현재 작품·프로젝트, 활성 계정·party·assignment, 기간과 scope를 다시 확인한다. 첫 공정의
등록 범위와 역할에 맞는 grant만 같은 transaction에서 생성한다. 프로필에서 직군을 바꾸거나
요청에 임의 역할을 적는 것으로 권한을 얻을 수 없다.

담당자를 교체하면 현재 공정 작업의 배정과 명시적 직군 연결을 함께 확인한 뒤 새 grant를 발급한다.
이 조건을 충족한 owner/admin/editor도 기존 범위 배정 화면을 사용하며, OFF인 프로젝트의 제한
편집 배정 대상은 기존 viewer/commenter로 유지한다. 현재 작업 배정에서 빠진 계정의 매핑 권한은
즉시 종료된다. 활성 직군 보호가 참조하는 원고 범위는 회수하지 않고 편집 배정 회수나 역할 중지로
권한을 회수해 원고 귀속·승인·재작업의 연결을 보존한다.

## 담당 편집과 실제 인계

원고에서 실제 담당 범위를 명시적으로 선택하면 페이지·레이어·프레임 편집 위치도 함께 맞춘다.
새 획·지연 완료·일반 변경·undo/redo·오프라인 발행·CRDT·REST 저장에 같은 보호 검사를 적용한다.
두 범위를 차례로 선택해 편집한 경우 실제로 허용됐던 현재 grant만 저장 문맥에 합치며, 계정·
정책 세대가 바뀌면 과거 문맥을 새 권한으로 전환하지 않는다.

실제 인계는 제작 관리자 또는 현재 작업의 실제 담당자가 실행한다. 편집 grant는 승인 시 끝나도
해당 담당자의 인계 권한은 별도로 확인한다. 화면의 인계 가능 표시는 힌트이고 서버가 최종 판정한다.

- 현재 작업의 제출과 필수 검수·승인이 완료되어야 한다.
- 현재 작업의 선행 입력이 최신이어야 하며, 두 번째 공정부터 직전 공정의 계보를 유지해야 한다.
- 다음 작업은 현재 승인 산출물을 dependency와 고정 입력으로 명시해야 한다.
- 인계는 작품 → 제작 프로젝트 → 정책 잠금과 revision CAS 아래에서 이전 grant 회수, 다음
  공정의 명시 배정 grant 생성, 이전 공정 동결, 승인 제출 근거 이력을 함께 확정한다.
- 마지막 공정의 승인 인계는 전체 매핑 범위를 동결하고 다음 grant를 만들지 않는다.

응답이 불명확하면 기존 관리 요청의 mutation ID와 원문을 보존한다. 사용자가 같은 요청의 결과를
확인하며, 새 ID로 인계를 자동 재실행하지 않는다. 계정·작품이 바뀐 뒤 늦게 도착한 응답은 적용하지 않는다.

## 승인 후 재작업과 이력 보존

인계·승인된 보호는 configure나 disable로 풀 수 없다. 일반 Production 명령으로 승인 작업의
status·scope·고정 입력·출력 목록·승인 제출 포인터를 바꾸는 우회도 거절한다.

관리자는 새 여덟 제작 작업을 만든 뒤 **새 제작 작업으로 재작업 시작**을 사용한다. 서버는 모든
작업 ID가 이전 공정과 다르고 승인 전 상태인지 확인하고, 현재 원고 revision CAS 아래에서
CRDT를 합친 현재 원고의 새 개정 snapshot을 기록한다. 기존 승인 제출본·작업·인계 이력은
보존하며, 새 공정만 다시 편집할 수 있다. 새 주기로 전환해도 과거 이력의 승인 작업 삭제·재개는
허용하지 않는다. 승인→완료 전환과 새 작업 추가는 기존 고정 산출물을 보존하는 범위에서 가능하다.

## 데이터와 배포 호환성

추가형 migration `0120_studio_role_pipeline_policy.sql`은 기존 정책 테이블에 nullable JSONB
`rolePipeline` 컬럼을 더한다. 기존 행의 NULL은 OFF이며 기존 policyVersion·targets·grants·
ownership·원고·사용자 설정을 다시 쓰지 않는다. 기존 정책 테이블이 없는 전체 편집 경로와
OFF인 프로젝트는 새로운 협업방 조건이나 제한 저장 경로로 바꾸지 않는다.

공유 정본은 [직군·그룹·공정 계약](../../packages/contracts/src/studio-role-pipeline.ts)과
[실제 변경 효과 검사](../../packages/contracts/src/studio-scoped-write-effects.ts)다. 기존 API의 효과
검사 import 경로는 재수출로 유지한다. 관리·인계·재작업은 기존 scoped-write API의 버전 CAS와
management receipt를 재사용하며, 전체 편집자의 저장은 기존 일반 저장 기능을 유지한다.

운영 적용은 검증된 정확한 main SHA, 필수 CI, 추가형 migration 원장·checksum·복구 계획,
정적 웹과 Core API의 개별 배포 증거를 확인한다. 운영 프로젝트를 자동으로 켜거나 기존 계정의
역할을 자동 변환하지 않는다. 이전 정상 이미지로 되돌리더라도 새 nullable 컬럼과 승인 이력은
삭제하지 않는다. 운영 배포 절차와 현황은 [인프라 지도](../operations/infrastructure-map.md)를 따른다.
