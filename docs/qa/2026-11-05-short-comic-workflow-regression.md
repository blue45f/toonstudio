# 동일 6컷 원고 제작 흐름의 수정·회귀 검증

상태: 구현 및 아래 범위의 로컬 실제 실행 검증 완료. 사람의 게시 확인·운영 검증·최종 후보 production build는 미완료다. 기준일은 2026-11-05이다. 최초 main은 `8d315c85d6fde4a3a30255612c756d3e299a95b0`이고, `2c626df4000fcfc32318faa793a61bea3ef0901b` 검증 뒤 추가된 CRDT 이력 수정 main `994e5ba34df98b6bcf1cb46c567456924a89dd68`까지 반영해 최종 검증했다.

## 변경 목적과 범위

기능별 시험만으로 단편 제작 완료를 주장하지 않기 위해, 실제 UI에서 제작한 「우산을 돌려주는 날」의 동일 6컷을 재사용한다. 원본 57개 요소, 페이지 ID·순서·대사·선·배경·채색, AI 이력과 게시 자체 확인 값을 보존한다. 원고·아카이브 schema, 저장 키, DB migration은 바꾸지 않는다. 운영 배포는 이 작업의 범위 밖이다.

| 문제 | 최소 수정 | 회귀 검증 경계 |
| --- | --- | --- |
| 회차에서 콘티를 열면 새 작품 생성으로 분리됨 | 저장 성공 후 기존 canonical 프로젝트·원고·회차로 이동. 복수 원고는 명시 선택 | 저장 실패 시 이동 차단, 보관 원고·잘못된 회차 거절, 원본 원고 유지 |
| 저장된 회차 샷과 작화 연결이 편집기에 없음 | 같은 편집기에 읽기 전용 샷 초안과 작화 이동 연결 | 같은 원고에서 workspace만 전환. 기존 페이지 자동 생성·교체 없음 |
| 파일 계획만 정상이어도 패키지가 준비된 것처럼 안내됨 | 파일 계획·구조·필수 자체 확인을 UI와 생성 경계에서 함께 평가 | 사람 확인이 남으면 안내·필수 점검 연결을 표시하고 정식 내보내기 차단 |

## 원본과 검증 층위

[고정 원고 fixture](../../tests/corpus/studio/short-comic-six-pages.json)의 `project`는 앞선 실제 브라우저 제작에서 내보낸 version 2 원고다. 원본 파일을 수정하지 않고 독립 시험 프로젝트·계정에 복사한다. `pagesList`의 JSON SHA-256은 `e06fa6d22e86f9a6755832ed19df57fb918997d557da27ab30c7ab900bb37e10`이며, 순서대로 여섯 페이지와 57개 요소를 비교한다.

| 검증 층위 | 사용하는 경로 | 완료 주장의 한계 |
| --- | --- | --- |
| 회차→콘티→작화 UI | [독립 브라우저 검증](../../scripts/verify-studio-episode-handoff.mjs) | 새 로컬 프로젝트의 공개 UI 가져오기·백업·재열기. 인증 서버 저장과 구분 |
| 실제 계정·공유 원고 | [6컷 통합 시험](../../tests/integration/api-web/studio-six-page-lifecycle.integration.test.ts) | 최초 원고 등록은 공개 API, 초기 CRDT는 실제 Web serializer. 기획부터 전 과정을 마우스로 입력한 시험은 아님 |
| 검수·인계 | 실제 AppModule·HTTP·CSRF·Socket.IO·PostgreSQL과 브라우저 | 자동화의 보존성 승인과 사람의 작품·권리·등급 승인을 구분 |
| 결과물 | 실제 캔버스 PNG와 기존 패키지 renderer·ZIP 경로 | 기술 검토용 묶음이며 정식 게시 승인 패키지는 아님 |

원본에는 과거 Undo journal과 완료된 AI 작업 이력이 없다. 따라서 시험 중 새로 추가한 획의 Undo/Redo와 원본 복귀만 검증하며, 존재하지 않는 과거 이력을 검증했다고 주장하지 않는다. 원래 `ownershipRightsConfirmed=false`, `audienceRating=null`인 값은 유지한다.

실서버의 정밀 보존 대조 범위는 `pagesList` 전체 및 `aiProvenance`, `writerRoom`, `characterBible`, `aiImageReferences`, `referenceBoard`, `publishPack`이다. 현재 페이지·저장 시각 등 운영 메타데이터를 포함한 프로젝트의 모든 필드가 전 과정에서 완전히 같다는 주장은 하지 않는다.

새 UI 시험은 독립 Chromium context와 새 시험 작품을 사용한다. 기존 브라우저 프로필·원고를 초기화하지 않으며 서버 계정 시험과 구분한다. 접근성 결과는 새 인계 영역에 한정한다. 수행 시간은 준비된 원고 fixture의 자동화 재생 시간이며, 사람의 단편 제작 시간이나 콘텐츠 제작 생산성 지표가 아니다.

[공개 UI 실행 영수증](evidence/2026-11-05-short-comic-fix/handoff-proof.json)은 실제 자동 복구 관찰, 원본 6컷 백업 대조, 화면 폭별 결과와 실행 당시 변경 제품 파일 17개의 SHA-256을 포함한다. 기준 main과 변경 파일 fingerprint를 함께 사용해 검증 후보를 식별한다.

[실계정 실행 영수증](evidence/2026-11-05-short-comic-fix/server-flow-proof.json)은 공개 API·실제 Web serializer로 준비한 같은 원고를 두 계정으로 검증한 결과다. 브라우저 Socket 수정 ACK 9개·거절 0개였고, 검수본 6장·재로그인 후 캔버스 PNG 6장·기술 ZIP의 회차 PNG 6장이 모두 협업 전 현재 후보 기준과 1440×1440 RGBA까지 동일했다. 검수 UI에서도 실제 업로드한 이미지 여섯 장의 로드를 확인했다. 승인 결정은 `automated-preservation-check`이며 사람의 창작 품질·권리·등급 승인이 아니다.

기술 ZIP은 838,465바이트이며 SHA-256은 `ee2d8658436c270cc208fb6cad438806c114df24d704bf27c3aab3e587fce1ee`다. 컷 PNG 6개·썸네일 1개·manifest·검증 보고의 총 9개 파일을 생성했다. 내부 보고는 `technical-review-only`, `releaseAuthorized=false`, `humanRightsAndRatingChecksPending=true`를 유지한다. 출처 내용 비어 있음과 썸네일 내용 검토 경고도 남겼다. 정식 게시 UI는 필수 사람 확인 7개로 계속 차단된다.

재열기 문제의 재현 순서는 새 로컬 작품 생성 → 원본 JSON 가져오기 → 기획으로 이동 → 동일 원고의 콘티·작화 → 새로고침이다. 수정 전에는 주소 `room`과 `sessionStorage`의 owner room이 달라 원고 소유자가 참가자로 분류됐고, 협업 잠금 때문에 OPFS·SQLite 복구 탐색을 시작하지 못했다. 복구 notice가 없고 초기 빈 페이지가 보였지만 이것이 원본 삭제를 뜻하지는 않는다. 최소 수정은 기존 소유권 확인·Web Lock과 자동 주소 갱신의 순서에 한정하며, 원고·저장 키·권한 정책을 바꾸지 않았다.

초기 시험의 실패도 통과 수에 포함하지 않는다. 실서버 준비에서 6컷을 하나의 CRDT 패킷으로 넣은 시도는 기존 byte budget에 차단되어, 동일한 Web serializer의 페이지·요소별 증분을 사용하도록 시험 준비를 고쳤다. 실제 DOM의 `menuitem`과 선택된 페이지 이름을 잘못 가정한 시험 locator도 수정 후 다시 실행했다. 제품 한도를 올리거나 잠금을 해제해 성공시킨 것이 아니다.

과거 `8d315c85d` 시점의 PNG와 현재 후보 검수 PNG는 픽셀까지 완전히 같지 않았다. 첫 컷은 2,073,600픽셀 중 5,955픽셀(0.28718%), 채널 최대 차이 48이었다. 원고 JSON은 이 시점에서 저장 시각을 제외하고 같았고, 시각 확인상 같은 그림·대사·배치였지만 렌더러·브라우저·실행 환경의 영향을 분리해 확정하지 않았다. 이 교차 버전 비교를 통과로 바꾸거나 임의 허용 오차를 추가하지 않는다. 현재 후보 안의 저장·협업 보존은 같은 브라우저에서 협업 전에 새로 내보낸 6장과 이후 검수·재로그인·기술 ZIP의 픽셀을 엄격히 비교하는 별도 시험으로 판정한다. 과거 PNG와 원본 자료는 그대로 보존한다.

## 재현 방법

1. 독립 로컬 웹과 폐기 가능한 시험 PostgreSQL을 준비한다. 실제 운영 DB·기존 사용자 계정·원고는 사용하지 않는다.
2. `TOONSTUDIO_SHORT_COMIC_ORIGIN=http://127.0.0.1:<웹 포트> node scripts/verify-studio-episode-handoff.mjs`로 공개 UI 연결과 게시 준비 안내를 검사한다.
3. `STUDIO_LIVE_POSTGRES_INTEGRATION_URL`, `TOONSTUDIO_RBAC_BROWSER_ORIGIN`, `TOONSTUDIO_SIX_PAGE_EVIDENCE_DIR`을 시험 환경에만 지정한 뒤 `pnpm exec vitest run tests/integration/api-web/studio-six-page-lifecycle.integration.test.ts --maxWorkers=1`을 실행한다. DB 권한과 migration 준비는 기존 PostgreSQL 통합 시험 절차를 따른다.
4. 각 보고서의 실제 실행 여부, 원본 SHA·6페이지 순서·57요소, 서버 저장 revision, PNG hash와 검수 매핑, 인계 후 계정별 재열기 결과를 함께 확인한다.

DB와 브라우저 주소가 없으면 실계정 통합 사례는 조건부로 건너뛴다. 기본 단위 CI의 fixture 검증 통과를 이 실계정 시나리오의 재실행으로 세지 않는다. 실행에는 운영 계정 대신 별도로 등록한 임시 계정 두 개를 사용한다.

## 사업계획서에 사용할 수 있는 구분

| 구분 | 기재 범위 |
| --- | --- |
| 구현 완료 | 기존 원고를 사용하는 회차·콘티·작화 연결, 파일 계획과 필수 점검을 합친 게시 준비 안내. 검증 결과와 별도로 코드 상태를 설명 |
| 실제 검증 완료 | 같은 6컷의 기기 원고 복구·회차/원고 인계, 임시 계정 두 개의 서버 저장·공유·포인터 Undo/Redo·재열기·검수 PNG·다음 공정 인계·재로그인, 현재 후보 내 이미지 픽셀 보존과 기술 ZIP. 각 층위의 준비 방식과 제한을 함께 기재 |
| 사람 확인·향후 개선 | 이야기·연출·작화 품질, 권리·출처·연령 등급, AI 고지 적정성, 실제 연재처 최종 접수, 서로 다른 실제 사용자·기기 협업과 운영 환경 확인 |

정식 최종 패키지 생성은 담당자가 필수 자체 확인을 마친 뒤 별도로 수행해야 한다. 기술 검토용 ZIP이나 자동화의 보존성 검수 통과를 사람의 승인·실제 연재 완료로 서술하지 않는다.

협업 인계의 실계정 시나리오는 `story-script`에서 `storyboard-conte`로 이동하는 경계다. 배경·채색·식자 등 모든 직군 조합의 다기기 인계, 검수 담당자가 UI로 창작 품질을 판정하는 사용성, 외부 메일 전달과 실제 object storage 제공자의 운영 동작까지 검증한 것으로 확대하지 않는다.

초기 서버 작품 등록은 API fixture 준비이므로, 로컬 6컷을 `초안 저장` 버튼으로 새 서버 작품에 등록하는 단계를 포함한 하나의 끊김 없는 UI 체험은 별도 미검증이다. 이는 사람의 권리·품질 판단이 남은 것과 다른 실행 범위의 제한이다.

## 복구와 배포

이번 변경을 되돌릴 때는 코드만 되돌린다. 기존 원고·OPFS·SQLite·로컬 저장소를 지우거나 새 포맷으로 변환하지 않는다. PR 생성·CI·병합·운영 배포는 별도 상태이며 이 작업에서는 운영 배포하지 않는다.

최종 실계정 시험은 신규 시험 사용자·작품을 정리하고 기존 blob 28개·object 56개가 바뀌지 않았음을 확인했다. 새 공유 blob 6개·object 12개의 메타데이터는 기존 하네스 정책에 따라 임의 삭제하지 않고 폐기 가능한 임시 cluster에 남겼다. API 4111 종료와 runtime 연결 0도 확인했다. 원본 원고·과거 PNG·실패 진단은 보존했으며 계정 비밀번호·세션·쿠키·raw 로그는 공개 증거에 넣지 않았다.
