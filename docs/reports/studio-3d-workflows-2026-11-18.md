# 3D 제작 도구와 가상스튜디오 작업 검증

## 브러시와 필터 선택

1,440px와 390px에서 각각 아홉 경로로 원고에 진입했다. 두 화면 모두 전체 도구 35개의 이름과 순서를 유지했고, 새 원고에서 각 도구를 실제로 눌렀다. 모바일 도구 목록의 각 행은 292 × 46px였으며 35개 모두 가운데를 눌러 명령을 실행했다. 프로젝트 메뉴에는 213개 명령이 있었다. 이 회차에서 실제 적용과 되돌리기까지 확인한 명령은 필터 58개와 보기·캔버스 명령 13개였다. [기기별 도구 조작 기록](studio-drawing-2026-11-19/tool-activation.json)

2026-11-19 로컬 Chrome에서 같은 벚꽃길 이미지를 새 원고에 불러왔다. 휴대폰에서는 하단의 **브러시**로 브러시 관리자를 열고 바로 옆 **필터**에서 효과를 선택한다. 가로 태블릿에서는 이미지를 선택해도 두 명령이 상단에 남는다. 1,024 × 768px에서 브러시 창을 닫으면 버튼으로 초점이 돌아왔고, Tab과 아래 화살표를 눌러 같은 이미지의 비파괴 필터를 열었다. [모바일 원고](studio-drawing-2026-11-19/mobile-drawing-manuscript.png) · [가로 태블릿 원고](studio-drawing-2026-11-19/tablet-drawing-manuscript.png)

프로젝트 메뉴에서는 도움말이 다음 줄의 필터를 가렸다. 여러 줄 메뉴의 도움말을 접근성 설명으로 옮기고 파일·편집·3D·필터의 빠른 메뉴를 원고 명령에 연결했다. 390px와 1,440px에서 3D 캐릭터를 골랐다가 취소하고 다른 캐릭터를 넣었다. 같은 원고를 다시 열었을 때 선택한 모델 이름이 유지됐다.

필터를 원고에 적용한 시점과 실제 그림이 바뀐 시점 사이에 진행 상태를 표시한다. 개발판에서 방사형 흐림을 적용한 원고는 7.55초 후 106,720픽셀 중 106,711픽셀이 달라졌다. 선택한 이미지 레이어에 바로 적용한 경우 97,344픽셀이 달라졌고 실행 취소 뒤 모든 채널이 원본과 일치했다. 연산 중 실행 취소하면 해당 진행 안내도 사라진다. [원고에서 기다리는 동안 보이는 안내](studio-drawing-2026-11-19/filter-render-pending.png)

## 지우개와 PNG 출력

| 유형 | 굵기 | 한 획의 농도 | 사용하는 곳 |
| --- | ---: | ---: | --- |
| 일반 지우개 | 20px | 100% | 선 일부를 깨끗하게 지울 때 |
| 정밀 지우개 | 4px | 100% | 선 교차점과 눈·머리카락을 다듬을 때 |
| 넓은 면 지우개 | 72px | 100% | 넓은 채색 면을 걷어낼 때 |
| 떡지우개 | 26px | 38% | 선을 남기고 밑그림 농도를 낮출 때 |
| 옅게 지우개 | 36px | 16% | 여러 번 지나가며 명암을 조금씩 덜어낼 때 |

일반 지우개와 떡지우개에 정밀 지우개, 넓은 면 지우개, 옅게 지우개를 더했다. 지우개의 굵기와 한 획에서 지우는 농도를 선택 전에 확인할 수 있다. 휴대폰의 지우개 버튼을 눌러 도구를 바꾸고 다시 누르면 목록이 열린다. [휴대폰 지우개 선택](studio-drawing-2026-11-19/eraser-picker-mobile.png)

390px 원고에서 한 획을 가로질러 지운 뒤 2배 크기 PNG를 직접 내려받았다. 정밀 4px는 폭 8픽셀, 넓은 면 72px는 폭 142픽셀에서 잉크가 줄었다. 옅게 지우개와 떡지우개는 획을 남겼다. 이전 불투명 PNG에서는 지운 자리가 투명해졌다. 수정 후 다섯 PNG 모두 종이는 알파 255였고, 한 번 실행 취소해 내려받은 파일은 지우기 전 파일과 모든 픽셀이 일치했다. [유형별 측정값](studio-drawing-2026-11-19/eraser-pixels.json)

같은 획의 가운데 3 × 3픽셀에서 잉크가 실제로 줄어든 비율은 일반·정밀·넓은 면 100%, 떡지우개 38.04%, 옅게 지우개 15.95%였다. 844 × 390px 가로 화면에서는 ‘창’ 메뉴의 ‘캔버스만’을 선택하고 직접 그린 뒤 실행을 취소했다. ‘도구막대 복원’을 누르자 하단의 일곱 도구가 돌아왔다. [가로 화면 캔버스 전용 보기](studio-drawing-2026-11-19/landscape-canvas-only.png)

## 드로잉 도구 디자인

2026-11-19 로컬 개발판에 ImageGen으로 만든 48개 도구 그림을 적용했다. 원고 도구 레일, 브러시 선택, 저장·기록·공유 버튼, 모바일 하단 편집 도크, 전체 도구 창이 같은 스프라이트를 쓴다. 전체 도구 창의 35개 명령에서 서로 다른 아이콘의 이미지 로드를 확인했다. 네 WebP의 합은 308,804바이트다. [데스크톱 원고](studio-drawing-2026-11-19/atelier-1440-studio.png) · [모바일 원고](studio-drawing-2026-11-19/atelier-390-studio.png) · [전체 도구](studio-drawing-2026-11-19/atelier-catalog.png) · [측정값](studio-drawing-2026-11-19/atelier-browser.json)

데스크톱의 전체 도구 창에는 분류와 첫 명령이 함께 보인다. 원고 상단에서 동기화 표시가 팀원 커서 조작을 19px 덮던 상태를 재현했다. 수정 후 두 버튼 사이에는 17px가 남았다. 모바일 390px에서 보이는 상단 버튼은 가로·세로 모두 44px 이상이었다. 강제색 모드에서는 선택한 펜과 지우개의 도형과 이름을 실제 데스크톱·모바일 스크린샷의 픽셀로 확인했다.

3D 모델러·배경·캐릭터 셰이퍼·VRM 포저·데생 인형·가상 스튜디오의 도구 그림을 진입 버튼과 작업대 제목에 맞췄다. 390px와 1,440px에서 여섯 화면을 열고 가로 넘침과 스크립트 예외가 없음을 확인했다. 작품 보관함은 실제 원고의 미리보기를 표시한다. 새 원고에 획을 저장하고 보관함의 최근 작업을 선택해 같은 작품·문서로 돌아갔다.

## 드로잉 진입과 3D 렌더

2026-11-19 실제 Chrome에서 WebGPU 엔진 파일 하나를 19초 늦게 전달하자 원고의 3D 배경이 ‘WebGPU 실행 실패’로 바뀌고 캔버스가 사라졌다. 파일 수신과 장치 초기화의 제한 시간을 분리했다. 같은 지연을 준 개발판과 정적 빌드 `9be4b96e345c`에서 WebGPU가 활성화됐고, 교실의 벽·칠판·창문·책상이 그려졌다. 기본 네트워크에서 운영 사이트의 교실도 확인했다. 사용자가 쓰던 기기와 원고의 실패 원인은 특정하지 못했다. [브라우저 기록](studio-drawing-2026-11-19/bg3d-cold-start.json) · [실패 화면](studio-drawing-2026-11-19/bg3d-cold-before.png) · [수정 후 교실](studio-drawing-2026-11-19/bg3d-cold-after.png)

별도 로컬 검사에서는 교실이 그려진 뒤 네이티브 GPU가 렌더 명령 하나를 거절하도록 했다. 오류 원인이 10.5초 뒤에도 남아 있었다. ‘WebGL2로 계속’을 선택한 후 WebGPU로 돌아왔을 때 오브젝트 39개의 ID와 순서가 같았고, 복구 전후 WebGPU PNG의 SHA-256이 일치했다.

선화 역할과 상세 모드를 함께 저장한 주소에서 사용자 제보와 같은 단계 막대와 상시 브러시 목록을 재현했다. 원고의 도구막대는 모든 역할과 작업 단계에서 하나로 통일했고, 단계 선택과 전문 메뉴는 ‘더보기 → 프로젝트·창 도구’에서 연다. 1,440 × 960px에서 같은 원고의 캔버스가 750 × 669px에서 1,362 × 860px로 넓어졌다.

가상 스튜디오에서 캐릭터의 충돌 위치와 화면에 표시할 위치를 분리했다. 일반 걸음에서는 접지한 발을 고정하고 카메라와 스프라이트가 같은 보간 위치를 사용한다. 하늘 캐릭터가 사무실의 같은 직선 구간을 걸을 때 제자리에 멈춘 프레임 전환은 수정 전 74회 중 12회, 수정 후 68회 중 0회였다. 화면에서 최대 발 들뜸은 1.82px에서 0.0001px로 줄었다.

3D 가상스튜디오에서는 로컬 테스트 계정 두 개로 같은 공간에 입장했다. 데스크톱에서 걸었을 때 모바일 화면의 상대 캐릭터가 105px 움직였고, 모바일 조이스틱으로 걸었을 때 데스크톱에서는 165px 움직였다. 각 방향의 마지막 7개 측정 프레임에서 멈춘 캐릭터의 좌표가 같았다. [양방향 이동 기록](studio-drawing-2026-11-19/office3d-motion.json)

## 가상스튜디오에서 작업 이어가기

- 게스트가 초대 코드로 스카이 포트에 입장한 뒤 새로고침하면 닉네임이 ‘크리에이터’로 바뀌고 로비에 남았다. 초대를 다시 확인한 뒤, 같은 공간에서 처음 발급받은 게스트 신원과 만료 시각이 일치하면 닉네임과 장소를 복원하도록 고쳤다. 실제 Chrome에서 새로고침 후 추가 클릭 없이 무대로 돌아왔다.
- 두 사람이 공유 보드를 연 상태에서 펜을 길게 한 번 움직였다. 수정 전에는 작업자 화면에 획이 3개 생겼고, 1,000 × 600 보드에서 첫 획은 (252, 120)에서 끊겼다. 수정 후 같은 입력은 두 모서리를 지나 의도한 끝점 (860, 192)에 도달했다. 로컬 저장이 한 번 실패하도록 한 뒤 ‘이 기기에 다시 저장’을 눌렀다. 터치 취소로 획이 추가되지 않았고, 새로고침 뒤 처음 그린 획 하나의 좌표가 모두 일치했다.
- 소유자와 편집자가 실제로 같은 방에 있어도 화이트보드에는 각각 1명만 표시됐다. 직접 연결에서 쓰는 접속 ID를 보드의 세션 ID와 맞춘 뒤 두 화면 모두 2명으로 표시됐다. 긴 획 48점은 상대 보드에서도 전부 같았고, 모바일 편집자의 메모가 데스크톱 소유자에게 도착했다. 390px 모바일에서 터치로 그린 29점의 선도 전송됐다. 화면상 시작·모서리·끝 세 위치와 입력 좌표의 차이는 각 0px였다.
- 격리 서버에서 A가 두 페이지에 각각 세 획을 그리고 원고 버전 2를 검수본으로 고정했다. B는 초대를 수락한 뒤 의견을 남겼고 빈 브라우저에 재로그인해 같은 의견을 읽었다. PostgreSQL에서 같은 검수본과 B의 의견 한 건을 확인했다. B의 승인 시도는 403, A의 승인 뒤 받은 ZIP 안의 PNG 두 장은 원본과 해시와 바이트가 일치했다. MinIO 원본 읽기는 격리 CA가 검증하는 전용 HTTPS 전달기를 거쳤다.
- 캐릭터 랩에서 저장한 발 포즈를 다시 열면 세 슬라이더가 모두 0°로 표시됐고 발끝만 움직여도 발목 회전이 사라졌다. 수정 후 왼발 굽힘 22°·기울기 12°·발끝 8°를 복원했다. 발끝을 14°로 조정하고 실행 취소·재실행을 거쳤다. 내보낸 두 GLB에서 왼발 뼈의 회전값 네 개는 그대로였고 발끝 뼈만 바뀌었다.
- 사무실 꾸미기에서 ‘네온 나이트’를 고른 뒤 캐릭터만 바꿔도 공간 테마가 ‘웹툰 아틀리에’로 돌아가던 문제를 고쳤다. 2D 사무실 테마 13개를 실제 캔버스에 렌더링하고 2D·3D 왕복 및 새로고침 뒤 선택을 확인했다. 방향 선택 버튼 네 개를 가리던 옆 카드도 정리해 데스크톱 클릭과 390px 모바일 터치가 모두 해당 방향 이미지를 바꿨다.

- 늦게 보드를 여는 경우도 별도로 확인했다. 첫 실행에서는 두 계정이 입장한 뒤 45초 동안 상대가 나타나지 않았다. 이때 신호 기록이 없어 원인은 확정하지 못했다. 이후 새 계정 두 개와 새 작품으로 작성자만 먼저 보드를 열어 긴 선을 그렸다. 모바일 팀원이 나중에 열어 48점을 모두 받았고, 서로 보드를 닫고 다시 열어도 2명·2획·3메모가 양쪽에서 일치했다. 마지막 실행은 12.01초였고 페이지 예외는 0건이었다.
- 데생인형 작업대의 리깅을 실제 GLB에 연결했다. 원본 51관절 중 왼손의 이름을 바꾸고 보조 관절을 추가했다. 패널을 닫거나 새로고침한 뒤, 내보낸 GLB를 다시 열면 52관절이다. 스키닝된 메시 160개, 기존 가중 정점 140,020개의 원본 데이터는 바이트 단위로 같았다. 새 보조 관절에는 웨이트를 자동 배분하지 않는다. Blender 5.3에서 기존 왼손 그룹의 정점 5,753개를 인덱스와 웨이트까지 대조했다. glbforge에서 두 파일 모두 경계 변·비다양체 변·퇴화 면이 0개였다. 이 해부학 작업 원본은 160개 프리미티브와 UV 없음으로 데스크톱 프로필 80점이며 해당 성능 기준을 통과하지 못했다.
- 배치용 해부 데생인형은 원본의 279,440개 삼각형과 본 51개, 재질 6개를 유지하면서 기본 패스 드로 수를 160에서 6으로 줄였다. 표면을 채색할 수 있도록 UV를 펴면서 파일이 6.80 MB에서 10.21 MB로 커졌다. Blender 5.3에서 정면·측면·굽힘 자세를 비교했고 원본과 같은 높이에 놓았을 때 정점 140,020개의 좌표 오차가 0이었다. GLB의 열린 경계·비다양체 변·퇴화 면과 UV 겹침은 각각 0건이었다. 지면 배치 파일과 기존 원고의 높이를 유지하는 파일을 따로 제공한다. 제작용 원본을 편집할 수 있고 배치용 파일은 가져오기로 연다. 실제 기기의 FPS는 측정하지 않았다.
- 공간 리더의 원통·돔·평면과 포커스를 실제 렌더러에 연결했다. 정적 빌드에서 화면 설정을 바꿔도 달라진 픽셀이 0개였다. 수정 후 원통에서 돔으로 바꾸면 데스크톱에서 45,834픽셀, 모바일에서 9,227픽셀이 바뀌었다. 실제 메시의 중심각은 90°와 120°였다. 일반 보기 복귀, 키보드와 모바일 터치 탐색을 확인했다. 이 두 기능의 변경은 위 정적 빌드 이후 개발 서버에서 검증했다.

화이트보드의 늦은 입장 실패가 다시 나타나 두 계정의 입장 순서를 확인했다. 두 사람은 같은 작품·장소에 있었다. 상대방의 첫 연결 요청과 후보 주소 두 개가 소유자 브라우저의 입장 승인보다 먼저 도착해 폐기됐고 새 요청이 45초 동안 없었다. 발신자가 기존 연결 요청과 후보만 한시적으로 다시 보내고 응답·퇴장·연결 교체 때 중단하도록 고쳤다. 해당 순서의 회귀를 포함한 전송 계층 검사 178건이 통과했다. 수정 후 새 소유자와 모바일 편집자가 실제 보드에서 첫 획 48점·최종 2획·메모 3개를 공유하고 보드를 다시 열었다. 74.235초가 걸렸고 페이지 예외는 0건이었다. 수정 후 추가 신호 계측은 입장 화면 준비 중 종료됐다.

리깅 작업대에서 왼손 바닥 메시의 가중 정점 602개를 대상으로 기존 왼손 본의 영향 중 40%를 새 보조 본에 옮겼다. 저장 후 작업대를 새로고침하고 GLB를 다시 가져와도 파일 해시가 같았고, 되돌리면 수정 직전 파일과 해시가 일치했다. Blender 5.3에서 보조 본을 0.65라디안 돌렸을 때 손바닥은 최대 30.34mm 움직였고 나머지 메시 159개의 위치 차이는 0이었다. 비율을 0으로 입력하면 적용할 수 없었다.

녹음 부스에서 WebM을 녹음하고 원고에 등록할 때 서버가 503을 반환하도록 했다. 기기에서 받은 파일과 패널을 다시 열고 새로고침한 뒤 받은 파일, 재등록 후 서버에서 내려받은 파일의 26,975바이트가 모두 같았다. 실제 MediaRecorder의 입력은 브라우저에서 만든 음원이었다. 예약 폼이 JSON을 일반 텍스트로 보내던 문제도 수정했다. 새 예약은 201이었고, 별도 조회에서 부스·참가자·30분 시간대가 일치했다.

작품 팀 공간의 투표는 작품·장소별로 PostgreSQL에 저장한다. 데스크톱 소유자와 390px 모바일 참여자가 익명으로 한 표씩 냈다. 새로고침하고 같은 요청을 다시 보내도 총 2표였다. 기명 투표는 참여자 이름을 표시했고 다른 장소에서는 빈 상태였다. 열람 전용 계정의 작성·투표, 작성 권한이 없는 참여자의 마감, 기한이 지난 제출은 거절됐다. 개인 작업실과 게스트 모드의 투표는 기기에 저장한다. 저장 실패 재시도와 손상된 원본 보관 후 다시 시작을 단위 테스트로 확인했다.

격리 DB는 빈 상태와 기존 원고가 들어 있는 0126에서 각각 0127까지 적용했다. 기존 원고를 보존했고, 같은 DDL을 다시 적용한 뒤 이미 저장된 투표·표의 해시가 일치했다. 런타임 역할에서 두 계정의 동시 생성·중복 투표를 검증했다. 저장소 구조 예산에는 새 정본 마이그레이션 파일 한 개를 반영했다.

tldraw의 공개 문서에서는 긴 선이 점 수 한도에 도달하면 마지막 위치에서 다음 도형을 이어 그린다. ToonStudio 공유 보드는 한 획을 최대 48점으로 주고받기에, 중간점 중 경로 변화가 가장 작은 점을 줄여 양 끝과 꺾이는 위치를 남긴다. 위 수치는 ToonStudio 실제 보드에서 측정했다. [tldraw의 자유선과 점 수 한도](https://tldraw.dev/sdk-features/draw-shape)

Miro의 보드 투표는 편집 권한으로 시작하고, 참가자가 패널을 닫았다 다시 들어와 진행 상태와 결과를 확인할 수 있다. ToonStudio의 팀 투표에서는 이 재진입 흐름과 계정당 한 표를 작품·공간별로 검증했다. [Miro의 투표 진행·결과 안내](https://help.miro.com/hc/en-us/articles/360017572274-Voting)

## 같은 원고의 드로잉 화면

원고 주소를 바꾸는 과정에서 보관함 방문 상태와 페이지 앵커가 사라지는 경우도 고쳤다. 실제 비공개 원고의 정식 주소, 기존 `/canvas?id=…`, `/studio?id=…`에서 같은 제목과 캔버스를 확인했다. 세 경로 모두 문서 조회가 200이었고 방 식별자, 모드, 실제 DOM에 있는 `#studio-canvas-workspace`를 유지했다. 뒤로가기를 한 번 눌러 원래 보관함으로 돌아갔다. [세 진입 경로의 검증 기록](studio-drawing-2026-11-19/manuscript-anchor.json)

일반 링크, 기존 통합 편집기 링크, 퀵모드, 설치형 웹 앱(PWA) 홈에서 같은 원고를 열었다. 변경 전에는 PWA 홈을 거친 것만으로 이전 앱바가 나타나고, 1,440px 화면에서 캔버스 너비가 1,362px에서 740px로 줄었다. 원고 편집기가 문서와 사용자 배치를 기준으로 도구막대를 선택하도록 고쳤다.

- 데스크톱 1,440 × 960px에서 네 경로 모두 캔버스가 1,362 × 860px로 화면 면적의 84.7%를 썼다. 모바일 390 × 844px에서는 네 경로 모두 390 × 719px였다. 선택 작업은 상단 44px 옵션 줄을 브러시와 함께 쓴다.
- 마우스 42좌표 획과 터치 38좌표 획을 각각 그렸다. 실행 취소로 획이 사라지고 재실행으로 돌아왔다. 저장 뒤 새로고침해 같은 획 ID와 좌표 수를 확인했다. 퀵모드·일반 모드와 브라우저 뒤로·앞으로 이동 중에도 편집기, 캔버스, 협업 룸이 유지됐다.
- 데스크톱에서 협업·검수, 댓글, 수정이력, 말풍선 도구를 하나씩 열어 목적 패널을 확인했다. 이 메뉴를 사용해도 드로잉 배치 선택이 덮어써지지 않는다. 좁은 화면에서 글자를 두 배로 키웠을 때 여러 저장 안내가 잘리던 문제도 수정했다.
- 전체 화면에서 **간단한 그리기**를 눌러 같은 원고에서 전환했다. 퀵모드는 펜, 일반 모드는 선택 도구를 활성화했고 뒤로·앞으로 이동해도 같은 도구가 돌아왔다. SQLite에 저장된 사용자 기본 도구와 패널 폭도 보존됐다.
- 개인 배치를 고른 뒤 두 화면 크기에서 원고의 8가지 주소 별칭과 새로고침을 검사했다. 집중 링크로 열어도 선화 작업공간의 선택이 유지됐다. 1,280 × 720px에서 데스크톱 캔버스 점유율은 82.2%였다. 세 화면 크기의 드로잉 도구막대에서 axe가 실행한 WCAG A·AA 규칙 위반은 0건이었다. 구주소 `/canvas`로 들어가도 파일·편집 버튼의 클릭 영역은 44 × 44px였다. 배포용 빌드에서 실제 원고 생성부터 시작하는 세 시나리오와 레이아웃 회귀 일곱 개가 모두 통과했다. 첫 실행에서는 모바일 탭이 한 번 종료됐으며 정확한 원인은 확인하지 못했다.

선화 기본 역할 링크와 이미 폐기된 역할 이름이 들어 있는 북마크에서도 기존 도구막대가 나타나는 분기를 수정했다. 같은 선화 역할 링크를 수정 직전 정적 빌드와 변경 후 개발 서버에서 각각 열고 펜을 눌렀다. 1,440 × 960px에서 캔버스가 가로 750px에서 1,362px로 넓어졌다. 그 시점 빌드는 기본 역할에만 통합 도구막대를 적용했고 검수·펜 디스플레이 등의 개인 배치는 이전 도구 구성을 열었다. 이후 확인한 개인 배치까지 통합한 결과는 문서 첫머리에 기록했다. 안드로이드·iOS의 Capacitor 래퍼는 웹과 같은 원고 편집기를 사용하면서도 이전 배치를 고르는 조건이 있어 이 진입 조건도 통일했다.

390 × 844px에서 작품 보관함을 열고 세로 웹툰 원고를 만들어 펜으로 한 획을 그렸다. 작업 파일을 내려받고 보관함의 **이어서 작업**으로 같은 원고를 연 뒤 새로고침해 다시 내려받았다. 두 파일에서 문서·페이지·획 ID, 좌표 20쌍, 필압과 기울기, 굵기 6, 색상 `#7c5cfc`가 모두 같았다. 생성 직후와 재진입 뒤 모두 통합 헤더 하나와 펜·지우개 각 하나가 보였다.

도구 레일 파일 하나의 응답을 보류하고 보이는 **전체 도구**를 눌렀다. 직전 빌드는 두 번째 클릭에서 열렸다. 수정한 빌드는 첫 클릭을 같은 원고에 보관했다가 파일이 준비됐을 때 도구 35개를 표시했다. 이어서 3D 배경을 검색해 도구 항목을 확인했다. Escape로 취소하거나 원고를 닫으면 보류한 요청도 사라진다.

## 팀 원고에서 고정 컷 다시 열기

원고의 배경 편집기에서 인물 포즈와 배치를 고정한 뒤 **팀에 새 컷 레이어 저장**을 누르면 합성 이미지가 새 레이어에 들어간다. 팀원이 레이어를 다시 열면 저장한 카메라, 표정, 모델과 기본색 채색을 복원한다. 기본 도형 배경을 지원한다. 업로드 모델의 원본 제공에 동의하면 서버가 VRM에 들어 있는 이용 조건을 확인한다.

- 실제 원고의 포저에서 소유자가 루미를 배치하고 새 컷 레이어를 저장했다. 다른 팀원이 새 브라우저로 같은 원고를 열어 레이어를 선택하고 기본 레일의 **3D 배경**을 눌렀다. 복구된 WebGL2 장면의 모델, 요소 ID, 컷 ID와 원본 해시가 소유자에게서 기록한 값과 일치했다. 팀 밖 계정의 원고·컷 조회는 모두 403이었고 이 흐름에서 브라우저 예외는 0건이었다. 원고 정식 저장을 막던 이미지 주소 해석과 StrictMode의 에셋 로더 해제, 선택한 컷을 무시하고 빈 3D 장면을 열던 레일·상단 메뉴·공정 버튼을 고쳤다.
- PostgreSQL에 원고·페이지·레이어를 묶어 장면과 합성 이미지, 첨부의 해시를 저장한다. 같은 작품에 같은 모델이나 채색이 이미 있으면 파일을 재사용한다. 배포 번들 모델은 실제 파일 108개의 SHA-256과 대조했다. 배포 파일이 달라진 버전에서는 해당 합성 이미지를 보고 버전 차이를 확인할 수 있다.
- 로컬 HTTPS MinIO에서 두 번째 계정이 합성 PNG 133,284바이트, 오리온 VRM 2,893,304바이트, 채색 PNG 70바이트를 각각 내려받았다. 세 파일의 SHA-256이 원본과 일치했다. 서명 없는 요청은 모두 403이었고 30초짜리 서명 주소도 36초 후 403이 됐다.
- 두 편집자가 같은 제출을 동시에 재시도해 모두 같은 원본을 열었다. 변조·첨부 누락은 400, 이미 보관한 레이어에 다른 장면을 쓰려는 요청은 409였다. 보기 전용 팀원은 원본 조회 200, 쓰기 403이었고 팀에서 제외한 뒤에는 장면·파일·새 서명 요청 모두 403이었다.
- 별도의 Chrome 프로필에서 업로드 모델 10,776,032바이트와 기본색 채색을 받았다. 개인 모델 라이브러리는 열기 전후 모두 비어 있었다. 무대에서 각각 13개 메시가 렌더됐고 두 재질에 채색이 적용됐다. 같은 카메라와 표정에서 채색 전후 640 × 640 이미지의 3,890픽셀이 달랐다.
- 새 작품 원본은 기존 개인 저장 공간을 사용하지 않는다. 추가형 DB 마이그레이션 `0125_studio_work_vrm_cut.sql`과 작품 에셋 저장소가 준비된 서버에서 쓸 수 있다. 로컬 새 DB의 125개 마이그레이션을 재실행해 체크섬이 일치했고, 분리된 실행 계정은 봉인 행의 조회·추가만 가능했다. 운영에는 적용하지 않았다.

## 채색 원본과 6패스 이력

2026-11-19 후속 변경에서 기본색·거칠기·금속성·발광·불투명도의 원본 PNG와 재질 슬롯을 팀 컷에 연결했다. 작품·페이지·배우를 확인한 뒤, 같은 PNG를 여러 슬롯이 공유하면 한 번만 보관한다. 세 가지 단일 값 채널은 서버에서 실제 화소가 불투명한 회색조인지 검사한다.

- 루미 의상의 발광에 흰 배율을 다시 적용하도록 고쳤다. 같은 카메라에서 칠하기 전후의 차이는 WebGL2 3,985픽셀, WebGPU 3,942픽셀이었다. 두 렌더러 모두 저장·재열기 뒤 차이는 0픽셀이었다.
- 업로드한 오리온의 왼쪽 대퇴뼈는 축별 배율이 최대 0.0031% 다르다. 기본 체형을 다시 열 때 이 값을 그대로 보존한다. 작업자 A와 새 브라우저의 팀원 B가 다섯 채널을 각각 칠했고 B는 원본 모델과 5 PNG의 7개 재질 바인딩을 복원했다.
- 팀원이 다시 연 3D 편집창이 원고 위에 남아 저장 버튼을 가리는 문제를 고쳤다. 두 계정의 실제 브라우저 세션에서 A가 오리온을 칠하고, B가 다섯 채널 전부를 수정한 뒤 새 컷으로 저장했다. B가 드로잉으로 돌아온 뒤 A가 PostgreSQL 원고에서 원본과 수정본 레이어 두 개를 함께 읽었고, A의 원래 컷 해시는 그대로였다. 두 계정이 받은 모델·PNG의 실제 바이트와 수정한 화소 값도 일치했다. 팀 밖 계정의 원고·컷·여섯 첨부 조회는 모두 403이었고 브라우저 예외는 0건이었다.
- 공동 원고의 3D 도구는 사용자·작품·페이지를 확인하고 서버가 편집 권한을 승인해야 원고에 삽입할 수 있다. 승인 대기 중 다른 사용자나 원고로 바뀌는 경우와 조회만 허용한 계정을 검사했다. 로컬 게스트 원고는 바로 편집할 수 있다. 권한과 진입 관련 검사 45개가 통과했다.
- 팀 6패스 v2는 원본 컷의 작품·페이지·모델·채색·배치를 확인하고 장면과 여섯 PNG가 모두 모이면 봉인한다. 예전 v1 원고는 기존 앱에서 읽을 수 있다. v2를 쓴 원고는 이를 읽을 수 있는 앱이 필요하다. 운영 DB와 분리된 PostgreSQL에 정식 마이그레이션 126개를 적용했다. 서로 다른 작품·페이지와 바뀐 배우 원본 거절, 불변 봉인, 접근 권한, 구버전 동기화를 포함해 DB 통합 검사 12개가 통과했다.
- PostgreSQL의 JSON 키 순서가 바뀐 원고는 고정 컷과 공유 장면의 해시가 일치하지 않아 다시 열리지 않았다. 원본 열람 권한과 같은 작품의 봉인 파일을 확인하고, 장면의 모든 값이 같을 때 원래 바이트로 복원한다. 새 브라우저에서 이전 원고의 주선 레이어를 열었을 때도 카메라·광원·6패스 출력 선택을 유지하도록 고쳤다. 카메라를 바꾼 원고는 검증에서 거절됐다.
- 그 원고에서 B가 다섯 채널을 다시 칠해 같은 여섯 레이어 ID에 새 버전을 저장했다. A가 다시 받은 두 버전에는 각각 장면과 여섯 PNG가 남았다. 같은 카메라에서 합성색 23,272픽셀, 톤 10,295픽셀, 그림자 5,255픽셀, 질감선 8,539픽셀, 주선 10,461픽셀이 달라졌다. 기하와 카메라를 고정한 깊이 패스의 차이는 0픽셀이었다. 격리 MinIO의 임시 인증서를 기본 Chrome은 신뢰하지 않아 이 새 기기 검사는 전용 CA로 서명 URL의 호스트·TLS·CORS를 확인해 실제 파일 응답을 브라우저에 전달했다.
- 새 작품과 세 계정으로 같은 흐름을 처음부터 다시 실행했다. 2,732 × 1,534px에서 B가 여섯 레이어를 저장하고, 주선을 다시 열어 다섯 채널을 바꾼 뒤 같은 여섯 ID에 두 번째 버전을 저장했다. A가 서버에서 받은 두 버전의 장면·PNG 7개씩을 확인했다. 두 버전의 PNG 12개는 DB 영수증의 SHA-256과 모두 같았다. 작품 밖 계정의 원고·컷 조회는 403, 브라우저 예외는 0건이었다.
- 400 × 480px WebGPU에서 오리온의 1K PNG 다섯 장과 7개 재질 바인딩을 한꺼번에 표시했다. 원본과 채색본에서 RGB 차이가 8을 넘는 픽셀은 25,348개였고, 채색 제거 뒤 원본과의 차이는 0개였다. 모델과 PNG 6개 파일의 SHA-256은 화면 조작 전후에 같았다.
- 400 × 840px 모바일 화면에서 실제 팀 컷의 오리온과 1K 채색 다섯 장을 다시 열고 불투명도를 칠했다. 편집용 브러시 버퍼는 열 때 0개, 처음 칠할 때 1개였다. 취소·재실행·적용 후 다시 열었을 때 불투명도를 공유하는 두 재질만 새 PNG를 가리켰고 나머지 네 장의 해시는 같았다. 포저가 집계한 메모리는 최대 56.46MiB로 64MiB 한도 안에 있었다.

## 서비스 경로 점검

게스트 세션만 응답하고 나머지 API는 503을 돌려주는 조건에서 데스크톱 경로 443개를 열었다. 최초 검사에서 본문에 도달한 경로는 400개였다. 중대 표식 21건 중 16건은 비로그인 제작 프로젝트의 로그인 안내를 오류로 처리한 경우였다. 게스트에게 로그인과 공개 샘플을 제공하고, 로그인 상태의 403·404·503 응답에는 재시도할 수 있는 오류 화면을 유지했다. 로그인 창을 닫았을 때 원래 경로·쿼리·해시도 보존됐다. 배포용 빌드에서 해당 16개 경로를 모두 다시 열어 로그인 안내로 분류됐음을 확인했다. 제보·기술 발표·구 캔버스 주소를 더한 19개 재검사에서 중대 표식은 0건이었다.

나머지 5개 표식은 4개 경로의 로딩에 걸린 시간과 관련됐다. 재방문에서 만화 편집기의 지우개 선택, 성장·IP 단계 전환, 스토리월드 설정 JSON 다운로드를 확인했다. 대표 17개 경로를 데스크톱·모바일에서 관찰한 34개 화면 중 모바일 홈 인트로가 늦게 나타난 사례가 한 번 있었다. 별도 방문에서 인트로가 사라진 뒤 둘러보기로 이동했다. 밝은 테마의 공용 헤더에서 검색·메뉴·로그인 글자의 실제 대비는 각각 6.25:1, 8.20:1, 8.41:1이었다.

제보 화면에서 유형별 버튼과 처리 상태 입력의 클릭 영역을 넓혔다. 기술 발표 화면에서 9px 안팎이던 작은 캡션과 절 이름을 12px로 키웠다. 수정한 두 화면을 데스크톱과 모바일에서 다시 열어 크기·가림 관련 감사 항목이 모두 통과했다. 제보 전용 브라우저 테스트는 비로그인 읽기, 입력 초안 보존, 서버 오류 재시도와 320~1,440px 레이아웃을 포함해 36개 모두 통과했다.
