# 웹툰 분업 협업의 대표 검증 조건 — 2026-10-29

상태: **target — 공식 자료를 참고한 검증 설계, 실제 제작팀의 사용 결과는 아님**.

2026-10-29 후속 사용자 확인의 최종 실행 범위는 **검증 후 main 병합까지**다. 앞선 PR 준비 제한은 대체됐고, 운영 배포·운영 DB·시크릿·DNS 변경은 범위에 없다.

2026-10-29 사용자는 실제 제작팀과 대표 회차를 직접 정하기 어렵다며 자료 조사와 판단을 위임했다. 팀 정보 응답을 기다리지 않고 아래 조건으로 구현과 통제 검증을 진행한다. 기존 [C1–C10 합격 조건](webtoon-collaboration-rea-benchmark-2026-10-28.md#6-최상위권을-위한-합격-조건)은 유지한다. 실제 사람이 참여한 현장 검증과 자동 모의 검증은 따로 기록한다.

## 2. 기본 프로필 결정

**기본 조건은 독립 계정 4개, 회차 60컷, 주간 마감, 검수 2회다.** 모든 수치는 통제 검증을 위한 설계 가정이며 제품의 사용량 제한이 아니다. 원고 품질·해상도·AI 기능을 줄이는 근거로 사용하지 않는다.

| 계정 | 맡는 역할 | 반드시 확인할 경계 |
| --- | --- | --- |
| 기획·콘티 담당 | 기획, 각색, 콘티 | 승인 콘티의 고정 입력, 변경 후 영향받는 작업과 재승인 요구 |
| 작화 담당 | 선화, 식자 | 동일 사람의 두 역할을 업무량에 합산, 후속 식자 작업의 입력 불일치 차단 |
| 외주 담당 | 배경, 채색 | 컷·기간에 한정한 배정, 범위 밖 수정 거절, 계약 기간 만료 뒤 현재 권한 검사 |
| 편집·검수 담당 | 독립 검수, 최종 납품 확인 | 제작 담당자와 다른 계정의 표, 필수 lane·정족수, 최종 원고와 승인 근거의 일치 |

실제 작업 시간 대신 구별 가능한 테스트 추정치를 사용한다. 예를 들어 동일 계정에 3시간과 5시간의 두 역할 작업을 배정하고 합계가 8시간인지 검사한다. 이를 실제 선화·채색의 표준 소요 시간으로 설명하지 않는다.

기본 의존성은 `기획 → 콘티 → (선화 ∥ 배경) → 채색 → 식자 → 검수 → 납품`이다. 병행 여부는 프로젝트 정책이며 일률적인 제작 규칙이 아니다. 배경 승인 뒤 선화를 시작하는 변형도 검사한다. 콘티 A2가 새로 제출되면 A1 기반 후속 출력의 승인·완료를 거절하고 과거 의견·결정은 보존한다.

## 5. 적용 상태

2026-10-29에는 공식 자료와 기존 source를 대조해 이 프로필을 결정했다. 선택 이미지 주소 갱신에서 전체 목록을 다시 받는 회귀 2개를 실제로 재현하고, 한 구간만 검증해 선택한 이미지의 URL·만료 시각만 교체하도록 수정했다. 관련 3 suites·130 tests가 실제 exit 0으로 통과했으며 새 lint·전체 게이트는 대기 중이다. 새 프로필의 전 과정 실행, 현재 후보 전체 타입·빌드·원격 CI, C9 운영 성능과 C10 현장 결과는 아직 통과로 기록하지 않는다. 그 검증 시점은 PR 준비 전용이었으며, 후속 사용자 확인으로 검증 후 main 병합까지 진행한다. 운영 DB·배포는 하지 않는다.

외주 프로필에서는 Production 배정의 범위·기간과 실제 원고 쓰기 권한을 반드시 별도로 확인한다. 팀 프리셋 화면도 [공정별 편집 제한이 서버 강제되지 않는 미리보기](../../apps/web/src/domains/creator/production-hub/TeamWorkspacePage.tsx)라고 명시한다. 따라서 배정 범위가 있다는 사실을 배정된 컷 밖의 Canvas·CRDT·Graph 쓰기가 서버에서 거절된다는 증거로 쓰지 않는다. 최초 읽기 감사에서 이 연결의 부재를 확인했고, 후속 소스에 실제 target·grant와 관리·저장·제출 경로를 추가했다. 프리셋 체험은 실제 정책으로 바꾸지 않았으며 전체 연결의 실행 검증은 대기 중이다.

## 6. 컷별 원고 쓰기의 구현 경계

상태: **target — 현재 소스에 근거한 구현 기준이며 기능 구현·실행 검증 완료가 아님**.

[ADR-0022](../adr/0022-studio-authority-identity-production-modes.md)는 의미 ID와 Authoring ID, 검수 버전의 권위를 구분한다. [페이지 bridge](../../apps/web/src/domains/creator/live/studio-crdt-page-bridge.ts)는 원고의 페이지·요소 ID를 실시간 문서에 보존한다. 최초 감사에서는 Production의 `ScopeRef`와 그 원고 ID를 서버가 보증하는 연결이 없었다. 후속 소스의 명시 target·grant를 이 절 기준으로 검증하며, [의미 ID 모델](../../apps/web/src/domains/creator/studio-foundation/studio-semantic-identity.ts)의 존재만으로 영속·적용을 판정하지 않는다.

컷 이름과 clip이 같은 폴더를 찾는 [frame-folder 경로](../../apps/web/src/domains/creator/studio-frame-folder.ts)도 권한 등록부로 사용하지 않는다. 검수 mapping은 저장 원고의 위치를 증명하며 편집권을 부여하지 않는다. master 요소나 근처의 stroke를 특정 컷 소유라고 추정하지 않는다.

다음 계약을 한 묶음으로 구현해야 제한 편집을 제공할 수 있다.

| 경계 | 구현 기준 |
| --- | --- |
| 명시적 원고 연결 | 관리 권한자가 Production 범위·작업과 실제 저장 원고의 page/frame/layer ID를 연결한다. 기준 revision·digest·연결 작성자·정책 버전을 서버에 남긴다. 이름·ordinal·좌표로 ID를 새로 만들거나 누락된 연결을 추정하지 않는다 |
| 실제 요소의 귀속 | 기존 요소·stroke·raster surface의 소유 컷·레이어와 새 요소를 만들 위치를 명시적으로 관리한다. 기존 요소를 다른 컷 소유라고 덮어쓸 수 없어야 한다. 여러 컷이 공유하는 raster를 요소 ID만 보고 한 컷 쓰기로 허용하지 않는다. 공정별로 제한할 때는 작업명만 보고 추정하지 않고 실제 허용 레이어·요소와 연결한다 |
| 권한 표현 | 작품 전체 `editor`와 제한 편집의 서버 capability를 구분한다. 기존 전체 편집 역할을 배정표만 보고 자동으로 축소하거나 확대하지 않는다. 제한 편집을 모르는 클라이언트·서버 경로가 기존 `edit=true`만 보고 전체 쓰기를 허용하지 않게 한다 |
| 모든 쓰기 경로 | REST 원고 저장, Graph 명령, JSON·binary CRDT, 가져오기·복구·도구 쓰기에 같은 서버 변경 범위 판정을 적용한다. 화면에서 선택 버튼만 숨기는 방법으로 완료하지 않는다 |
| 원자 처리 | 현재 서버 시각의 활동 기간·현재 정책 버전·현재 membership을 실제 저장과 같은 잠금·transaction에서 확인한다. 거절한 변경은 메모리 정본·DB·이력에 부분 적용하지 않는다. 요청 영수증도 올바른 정책 버전과 연결한다 |
| 변경·만료·복구 | 역할·연결·기간이 바뀌면 기존 세션과 대기 중인 쓰기를 다시 검사한다. 오프라인 초안은 보존하되 과거 편집권으로 자동 업로드하지 않는다. 일반적인 공동 편집의 내용 변경만으로 작품 전체 digest가 달라졌다고 모든 정상 편집권을 계속 무효화하지 않는다 |

원고 연결의 기준 revision은 최초 연결을 검증하는 근거다. 실제 편집에서는 안정 ID의 현재 존재·귀속과 현재 정책을 검사해야 하며, 다른 담당자의 정상 변경 때문에 동일 작품 전체를 잠그는 방식으로 대체하지 않는다. 지원할 수 없는 모호한 귀속은 제한 권한을 새로 부여하는 단계에서 드러내며, 원본 raster를 조용히 분할·변환하거나 품질을 낮춰 해결하지 않는다.

2026-10-29 구현 초안은 안정 target과 현재 공정 grant를 분리한다. target의 최초 연결 task·불변 원고 근거·객체 귀속은 유지하고, 현재 grant의 task·assignment·계정·기간·범위로 다음 공정의 인계를 검증한다. 같은 객체를 다른 target으로 옮겨 인계를 흉내 내지 않는다. 다각형 컷도 공용 실제 자식 클립으로 연결하되, 그 기하를 객체의 소유권 증명으로 사용하지 않는다. 제한 저장·실시간·파생 캡처·업무 제출의 전체 경로와 관리 UI는 최종 검증 전이다.

합격 증거에는 허용 컷 수정과 새 요소 생성, 다른 컷의 수정·삭제·귀속 변경 거절, 공용 raster·문서 전역 설정 보호, 서버 시각 만료, 역할 회수 뒤 기존 세션·오프라인 update 거절, 동일 요청 재시도, 기존 전체 편집 역할 호환성을 포함한다. REST·Graph·CRDT 각각에서 실제 변경 전후의 정본과 영수증을 대조해야 한다. 이 증거가 없는 상태에서는 컷별 원고 쓰기 격리를 제공한다고 표시하지 않는다.

## 7. 빈 프로젝트의 첫 제출·재제출 경로

상태: **migration — 실제 캡처의 첫 제출 소스와 순수 Core 54개 통과, API source·UI·실제 DB·통합 검증 대기**.

현재 `createProductionProjectAggregate`는 작업·산출물·제출본을 빈 배열로 만든다. 워크플로 작업 생성은 task를 만들지만 입력·출력 ref를 채우지 않는다. 등록된 Web 경로의 검수 요청은 `upsert-task` 또는 작업 상태 변경을 보내고, `upsert-submission` 생성은 기존 제출본의 검수 상태 변경뿐이었다. Studio의 `kind=submission` revision과 Production의 `Submission`은 같은 객체가 아니며, 원고 캡처가 Production 제출본을 자동 생성하지 않는다.

실제 Canvas 저장은 CreatorWork 문서·revision을 기록하며 generic Graph artifact를 자동 등록하는 Web 호출자는 확인되지 않았다. 실제 검수 캡처는 작품별 Graph review artifact를 만들지만 `scope`는 Graph 프로젝트 범위다. 반면 워크플로가 만든 회차 작업과 현재 이미지 검수 resolver는 회차 범위의 정확한 일치를 요구한다. generic artifact의 계약에 회차 필드가 있다는 사실이나 테스트 fixture의 회차 scope만으로 이 실제 UI 연결이 존재한다고 판정하지 않는다.

따라서 실제 capture 선택과 함께 사용자가 저장된 페이지·프레임을 해당 작업의 산출물로 명시적으로 연결하는 경로가 필요하다. 서버는 같은 작품·완료된 capture 영수증·고정 원고 tuple·page/frame mapping·해시·중복 여부를 검사하고 작업의 업무 범위와 함께 기록해야 한다. 문서 전체를 연결하는 선택은 전체 원고 연결이라고 표시하며, 그 원고가 특정 회차만 포함한다고 추정하지 않는다. mapping의 Authoring ID와 Production의 회차·컷 ID도 동일하다고 간주하지 않는다. 새 연결 증거를 읽는 별도 경로를 구현하되 기존 `artifactWithinScope`를 전역 완화하거나 Graph 원본 scope를 덮어쓰지 않는다. 이는 원고 사용 범위의 명시적 연결이며 6절의 실제 쓰기 권한을 자동 부여하지 않는다.

따라서 API·fixture로 산출물을 미리 넣은 검증만으로 첫 제출·수정 후 재제출의 UI 완주를 입증하지 않는다. `ProductionStudioRevisionWorkspace`도 이미 존재하는 제출본을 연결한다. 개요 화면에서 이 Workspace로 현재 사용자 ID가 빠지는 경로는 Overview → Management → Workspace로 명시적으로 전달하도록 소스를 수정했다. 계정 ID가 없거나 비어 있으면 역할을 선택하지 않는다. 관련 실행 검증은 아직 대기 중이며, 계정 미연결 외주 party를 현재 사용자로 간주해서는 안 된다는 조건을 유지한다.

첫 제출에는 산출물 정의·작업의 출력 연결·새 제출본이 함께 필요하다. 이를 하나의 사용자 동작으로 제공한다면 좁은 `submit-task-output` 명령이 기존 `mutateProject` transaction 안에서 세 변경을 검증·저장하도록 한다. 일반적인 임의 명령 배열을 추가하지 않는다. 기존의 산출물·작업·제출 명령 세 개를 순차 호출하면서 전부 원자적으로 처리됐다고 표현하지 않는다.

UI는 실제 작품의 저장된 Studio revision과 정확한 ID·digest·lineage를 선택하게 하고, 현재 계정의 활동 기간·산출물 범위에 맞는 역할을 사용한다. 실제 원고 쓰기 권한은 6절의 별도 계약이다. 새 산출물의 범위는 작업 문맥에서 결정하고 완료 기준·형식을 명시한다. 작업 입력을 임의의 head나 예시 값으로 채우지 않는다. 선행 작업이 있는 경우 승인된 입력과 고정 ref를 확인하며, 최초 작업의 기준 원고도 사용자가 명시적으로 선택하도록 한다.

소스 확인은 같은 저장 transaction에서 현재 권한·영수증·expected revision을 확인한 뒤 수행해야 한다. Graph 프로젝트 ID와 Production 프로젝트 ID는 다른 이름공간이므로, 실제 artifact·저장 revision·digest와 연결된 `workId`를 대조한다. 서비스에서 별도 DB 연결로 목록을 미리 읽는 방법만으로 이 조건을 충족했다고 판정하지 않는다. 현재 Web bridge의 revision 번호는 목록의 생성 시각·ID 정렬 순위이고 Studio revision row에는 Production의 lineage·단조 증가 번호가 없다. 또한 Canvas의 `visual`과 식자·최종본 연결의 `integrated` 계약이 다르다. 첫 제출 명령을 구현하기 전에 이 권위를 정해야 하며, 순위나 공정명을 정본 번호·lineage로 추정해 제출하면 안 된다.

후속 읽기 조사에서는 새 DB 열 없이도 활용할 수 있는 서버 좌표 후보를 확인했다. 일반 commit·restore는 artifact 잠금 안에서 `studio_operation.sequence`를 계산해 결과 revision과 영수증에 남긴다. 클라이언트가 지정할 수 있는 `operationLast`와 구분한다. 다만 결과 revision의 operation 연결에는 유일 제약이 없으므로 정확히 한 연결만 인정해야 하며, 최초 저장과 검수 캡처에는 별도 증명이 필요하다. 특히 캡처는 한 sequence로 원본 checkpoint·submission·review snapshot을 만들고 마지막 snapshot만 operation에 직접 연결한다. 나머지를 연결 없음이라는 이유로 최초 버전으로 취급하면 안 된다. 기존 완료 영수증과 세 단계 원고 연결을 함께 확인해야 한다. 이 좌표를 전체 저장본의 연속 순위라고 표시하지 않는다.

lineage는 Graph의 불변 저장 필드가 아니라 명시적인 Production 문서 역할의 업무 투영이다. 새 소스 초안은 실제 review snapshot ID·digest를 보존하고 원고 번호는 검증된 CreatorWork `sourceServerRevision`을 사용한다. `captureSequence`는 세 단계 캡처 연결을 증명하는 별도 좌표이며 원고 목록 순위로 해석하지 않는다. 같은 캡처의 서로 다른 페이지를 여러 업무 산출물로 쓰는 경우에는 실제 Production 제출 ID를 optional `productionSubmissionId`로 함께 기록해 입력 핀을 구별한다. 레거시 참조는 이 필드 없이 보존하며 기존 원고·승인 이력을 재작성하지 않는다. 새 `sourceEvidence.version=1` 정책의 원고 선택·검수 reader와 공개 Production 참조 스키마를 함께 연결했다. 기존 Graph 목록 응답에는 새 필드를 일방적으로 추가하지 않았다. 이 구현은 아직 타입·단위·HTTP·브라우저 검증 전이다.

재제출은 새 제출 ID와 저장 revision을 사용해 이전 승인·의견·입력 ref를 보존한다. 미확인 쓰기는 원래 mutation ID·요청 본문·원고 선택을 보존하고, ACK 또는 같은 영수증의 복구를 확인한 뒤에만 초안을 비운다. 계정 전환·권한 회수·revision 충돌·저장 오류에도 중복 산출물을 새로 만들지 않아야 한다.

조건부 승인·승인·완료·취소·범위 밖 task에 새 제출을 추가해 상태를 그대로 둔 채 승인 포인터만 해제하는 경로는 새 명령에서 거절한다. 기존 workflow가 허용한 변경 요청 전환 뒤 재제출하거나 후속 작업을 생성해야 한다. 종료 task에 없는 다시 열기 전환을 새 제출이 암묵적으로 만들지 않는다. 캡처 subject도 실제 공개 Studio ID 계약을 DTO·preview·공유 증명에서 같이 사용하고 댓글·인계용 레거시 참조 범위는 그대로 둔다. 현재 소스 초안에 반영했으며 실행 검증 전이다.

합격 검증은 예시 산출물이 없는 실제 신규 프로젝트에서 회차·공정 작업 구성 → 기준 원고 저장·선택 → 산출물과 첫 제출 등록 → 독립 검수의 수정 요청 → 새 저장본·새 ID 재제출 → 승인·납품 확인을 수행한다. UI 밖의 직접 API 입력이나 앱 내부 상태 주입으로 누락 단계를 대신한 경우는 부분 검증으로 기록한다. 통제된 자동 완주와 실제 사람의 현장 결과는 계속 분리한다.

2026-10-29에는 현재 사용자 귀속 누락을 확인하기 위해 실제 Overview → Management → Studio 원고 연결 컴포넌트를 유지한 2개 회귀를 추가 작성하고 위 전달 경로를 수정했다. 같은 역할의 다른 연결 계정과 미연결 외부 party를 함께 두고 정확한 현재 계정의 역할 ID를 기대한다. 현재 사용자 ID가 없을 때는 미연결 party를 빌려 쓰지 않아야 한다. 기존 Workspace 양성 fixture도 실제 연결된 demo 계정과 정확한 assignment를 지정하도록 교정했다. 이 UI 회귀는 미실행이다.

신규 제출 범위 6개 회귀는 허용된 단일 실행에서 1개 실패·5개 통과했다. 자기 역할의 회차 범위 밖 제출이 실제로 거절되지 않는 것을 확인했고, 이후 신규 제출에만 범위 검사를 추가했다. 기존 제출 상태 변경에는 소급하지 않고 프로젝트 전체 담당자와 산출물 누락 시 기존 검증 경로를 보존한다. 별도 허용된 수정 후 단일 실행에서는 같은 파일의 21개 전체가 단일 worker·actual exit 0·skip 0으로 통과했다. 명시한 19입력 해시가 전후 같고 소유 process group 종료를 기록했다. 새 첫 제출 명령·화면·DB 증명의 통과를 뜻하지 않는다. 기존 미리보기 130개 통과도 이후 새 reader·업무 범위 표시 변경까지 검증한 결과가 아니다.

새 첫 제출의 순수 Core 2 suites·54 tests도 별도 단일 worker 실행에서 actual exit 0·skip 0으로 통과했다. 명시한 21입력 해시와 변경 목록이 전후 같으며 소유 process group 종료를 기록했다. 첫 제출 후보·독립 입력 귀속·종료 task 거절·현재 모든 출력의 승인 집계를 다루며, 실제 HTTP·DB·Web 완주와 현장 검증은 계속 별도 미완료다.

첫 제출 소스 초안은 `submit-task-output` 하나로 기존 transaction·CAS·영수증 경계를 재사용한다. 현재 소유권·멤버십과 역할 기간·범위를 확인하고, 같은 transaction에서 공유 캡처 증명 쿼리·완료 영수증·정확한 원고 chain·이미지 객체 소유·mapping을 대조한다. 산출물 정의·작업 출력 연결·새 제출·포인터·사용 근거는 하나의 candidate aggregate로 구성한다. UI는 실제 저장 원고의 이미지와 페이지·프레임을 보여 주며, 최초 기준 원고·현재 입력·선행 승인 출력을 명시적으로 선택하게 한다. 원고 사용 근거는 편집 권한을 부여하지 않는다. 기존 입력 중 레거시 외부 참조의 실제 파일 존재까지 새 출력 근거가 일괄 증명한다고 주장하지 않는다.

아직 필요한 증거는 새 코드의 단위·타입·하네스, 실제 PostgreSQL/HTTP에서의 원자 저장·권한 회수·중복 요청, 실제 빈 프로젝트에서 여러 계정의 UI 완주, production 성능이다. 현재 소스 초안은 캡처 원고 경로이며 Writer Room의 서술 원고 등 다른 원고 형태의 완주도 따로 확인해야 한다. C1–C10 전체 통과나 최상위권 달성으로 판정하지 않는다.
