# 오프라인 CRDT 기기 보관 복구 — 2026-11-01

## 현재 상태와 범위

문서 상태는 `current`이며, 운영 완료가 아닌 구현 후보의 확인된 검증 결과를 기록한다.

이 변경은 main `21f269e84cbdd640959ef4cd880002f45c66ee9d`를 기준으로 한 후속 교정이다.
PR #2631의 충돌 해결 기능을 유지하면서 Yjs 복구 대기열의 저장 재시도와 요청 불변성을 보완한다.
운영 배포는 수행하지 않는다. 병합과 최종 실제 브라우저 검증은 각각 별도 결과로 확정한다.

앞선 실제 r8에서는 두 계정의 온라인 입력·획 최종화·ACK·PostgreSQL·공유 저장·양쪽 PNG가
통과했다. 오프라인 입력 이후에는 `durability-risk`가 지속됐고, 제한 진단 r10에서도 같은
보호 상태가 재현됐다. r10에는 구체적인 storage 오류 코드가 없어 아래 소스 결함을 r10의
직접 원인으로 단정하지 않는다. 이번 단위 검증은 최종 main의 실제 오프라인·재접속·재열기와
두 충돌 선택 검증을 대신하지 않는다.

## 확인한 결함과 교정

### 연결 종료 뒤 기기 저장 재시도

실제 `disconnected` 이벤트는 `authoritativeSyncReady`를 해제한다. 기존 `runDrain`은 이때
기기 저장 결과가 실패여도 즉시 반환해, 아래 오프라인 분기에 있던 재시도 예약에 도달하지
못했다. 저장이 750ms 제한 뒤 늦게 끝난 경우도 같은 요청의 보호 상태를 다시 확인할 계기가
없었다.

두 대기 분기를 합쳐 기존 backoff를 재사용한다. 실패한 저장은 원래 ID와 본문으로 다시
시도하며, 실제 저장 성공 뒤에만 durable 상태로 회복한다. 서버의 정본 동기화가 확인되기
전에는 publish하지 않는다. 기존 750ms 제한과 timeout 이후의 늦은 결과 처리도 유지한다.

### 이미 보관한 요청의 ID와 본문

기존 coalesce는 ready tail의 ID·client sequence를 유지하면서 payload를 바꿨다. 메모리
시험 보관함은 이를 덮어썼지만, 실제 SQLite와 서버는 같은 ID의 다른 본문을 거절한다.

런타임 전용 `persistenceStarted`를 최초 put 예약 직전에 설정하고, 복원한 ready 요청에도
설정한다. 한 번 보관을 시작한 요청은 성공·실패·timeout과 관계없이 ID와 본문을 고정한다.
다음 배치는 기존 enqueue 경로에서 새 ID와 증가한 sequence를 받고, 이전 요청은 그대로
보존한다. SQLite의 불변성 검사, 서버 멱등 계약, wire와 저장 schema는 변경하지 않는다.

기기 보관을 시작하지 않은 메모리 배치의 병합과 기존 40ms 배치·48KB 프레임 상한은 유지한다.
영속 저장 이후에는 배치마다 별도 요청을 보관하므로 이전 병합 기대보다 행과 재연결 요청 수가
늘 수 있다. 기존 65,536행·256MiB 한도와 명시적 backpressure·자료 보존 계약은 유지한다.

### 저장 회복 뒤 반복 순회

초기 교정은 이미 durable인 정본 대기열도 300ms마다 다시 순회했다. 현재 정본 권위를 기다리는
durable 큐는 새 입력·연결 이벤트가 깨우도록 하고, 실패한 저장만 backoff를 예약한다.
mesh·local 경로의 기존 예약은 유지한다. 저장 await 도중 연결과 실제 정본 동기화가 완료된
경우에는 현재 authority를 다시 검사해 후속 drain이 원래 요청을 전송·승인하도록 한다.

영구 저장 실패는 열린 편집기에서 재시도해도 보호 성공으로 표시하지 않는다. close 후에는
추가 put·상태 발표가 없으며, 저장이 회복돼도 서버 ACK가 없는 요청은 pending으로 유지한다.
저장 중 실제 재연결이 끝나는 경합도 수동 flush나 새 입력 없이 원래 ID의 승인으로 수렴한다.

기존 시험 fixture를 작은 지원 파일로 보존 추출했다. 기존의 durable 요청 5개를 같은 ID로
덮어쓰던 기대는 저장 전 메모리 병합 시험으로 경계를 명확히 하고, 저장 후 불변성은 별도의
두 회귀로 검증한다. skip·삭제로 실패를 숨기지 않는다. 기존 초과 파일은 최초 줄 수를 넘기지
않으며 새 파일은 800줄 미만이다.

계획·입력 해시·원문 로그·소유 프로세스 종료·정식 예약 반환 기록은 로컬 Git 관리 영역의
`cleanup-evidence-20261030/collaboration-conflict-resolution-20261101/persistence-recovery-r1`
및 대응 `runs` 디렉터리에 보존한다. 각 실행은 독립 900초 창과 120초 정리 여유를 사용하며,
새 실행 전 메모리 여유 40% 이상과 공유 슬롯 해제를 확인한다. 실패·진단 완료·기능 통과는
구분하고, 실제 r10의 미관측 오류 코드를 새로 추정해 기록하지 않는다.

번들은 격리된 기존 작업 폴더에서 공개 입력으로 생성했다. 추적된 `.env.production`은 승인한
main blob과 같고 공개 키 4개만 포함한다. 부모 환경의 VITE 값은 승계하지 않았고 별도 로컬
환경 파일은 없었다. 전체 19,781파일·5,788,207,973바이트의 SHA-256 목록을 기록했으며,
이 단계에서는 산출물과 작업 폴더를 옮기거나 보관 처리하지 않았다. 후속 담당에게 같은
작업 폴더를 순차 인계하고 최종 검증 뒤 공식 보관·정리를 진행한다.
