## 1. 요청과 권리 상태

2026-10-15 저장소 소유자가 "Mixbox 제작사 관계자와 내재화(독립 구현) 거래를 하고 허락을 받았다. 직접 쓰는 것이 아니라 코드와 작동 원리를 분석해 유사하게 구현해 달라"고 요청했다.

## 2. 분석 방법과 범위

- 읽은 것: `mixbox.esm.js`의 RGB→잠재, 잠재→RGB, 선형 보간, 색 입력 정규화 함수와 README의 사용법.
- 읽지 않은 것: 대용량 격자표(상수 배열)의 값. 값 자체는 구현에 필요하지 않고, 복사할 수 없기 때문에 옮기지 않았다.
- 논문: Šárka Sochorová, Ondřej Jamriška, "Practical Pigment Mixing for Digital Painting", ACM Transactions on Graphics 40(6), Article 234 (SIGGRAPH Asia 2021). 초록 수준만 확인했다. 잔차 항과 안료 기저의 세부는 본문으로 확인하지 못했으므로 구현 전에 논문 본문으로 다시 확인한다.

## 3. 작동 원리

### 3.1 한 줄 요약

RGB 색을 "안료 4종의 농도 + 3채널 잔차" 7개 숫자(잠재 색)로 바꾸고, 섞을 때는 7개 숫자를 가중 평균한 뒤, 농도에서 색을 만드는 비선형 식에 통과시켜 다시 RGB로 돌려보낸다. [코드]

### 3.2 잠재 색의 구성 [코드]

잠재 색은 숫자 7개다. 앞 4개는 안료 농도이고 합이 1이다. 뒤 3개는 R·G·B 잔차다. 농도는 3개만 저장하고 네 번째는 1에서 앞 세 개의 합을 뺀 값으로 만든다.

### 3.3 농도 → 색: 3차 다항식 [코드]

농도 4개로 sRGB 색(0~1)을 만드는 식은 네 변수의 3차 항 20개의 가중합이다. 네 변수의 3차 동차 단항식은 정확히 20개(세제곱 4개, 제곱×1차 12개, 서로 다른 셋의 곱 4개)이고, 합이 1이라는 제약 때문에 세 변수 3차 다항식 전체를 표현한다. 채널마다 계수 20개가 따로 있다.

[추정] 이 식은 네 안료의 Kubelka–Munk 혼합 결과를 빠르게 근사하려는 적합식으로 보인다. 코드에는 계수만 있고 유도 과정은 없으므로 사실로 확인한 것은 아니다.

### 3.4 색 → 농도: 격자표 룩업 [코드]

입력 RGB를 0~1로 잘라 낸 뒤, 축당 64칸인 3차원 격자표에서 8개 이웃을 삼선형 보간해 농도 3개를 얻는다. 표는 농도 3개를 각각 한 장씩, 바이트(0~255)로 저장한다. 즉 "이 RGB 색에 가장 가까운 색을 내는 농도"를 미리 계산해 둔 역함수 표다.

### 3.5 잔차 [코드]

잔차는 `입력 RGB − 다항식이 만든 색`이고 자르지 않는다. 네 안료로 만들 수 없는 색(안료의 색역 밖)도 잔차가 차이를 담아서 왕복해도 원래 색으로 돌아온다. 정수 입력은 격자표 양자화 때문에 오차가 생기지 않도록 잔차를 같은 식에서 계산한다.

### 3.6 잠재 색 → RGB [코드]

`다항식이 만든 색 + 잔차`를 0~1로 자르고, 정수 출력이면 255를 곱해 반올림한다.

### 3.7 혼합 [코드]

두 색(또는 여러 색)을 섞을 때는 7개 숫자를 가중 평균(선형 보간)하고 3.6의 식으로 색을 만든다. 알파는 따로 선형 보간한다. 선형 RGB용 함수는 입출력에서 sRGB 변환만 더하고 잠재 공간의 정의는 같다. 기본 경로는 sRGB로 인코딩된 값에서 곧바로 동작한다.

### 3.8 왜 안료처럼 섞이는가 [추정]

농도는 선형으로 섞이지만 농도→색 식이 비선형이라서, 같은 비율의 선형 RGB 혼합과 다른 결과가 나온다. 예를 들어 파랑과 노랑의 농도 평균은 한쪽 안료만 높은 농도를 갖는 색들의 중간이고, 이 식이 그 중간을 초록 쪽으로 보낸다. 이 해석은 구조에서 나온 설명이며 이 분석에서 수치로 검증하지 않았다.

### 3.9 성질과 한계 [코드, 추정 구분]

- 단일 색에 가중치 1을 주면 같은 색이 돌아온다(잔차 덕분에 무손실). [코드]
- 비용은 색마다 격자표 8점 보간 3장과 다항식 20항 계산, 혼합은 7개 숫자 연산이다. [코드]
- 색역 밖의 색은 잔차 항이 선형으로만 섞이므로 안료다운 혼합이 되지 않는다. [추정]
- 안료 기저가 네 가지로 고정이라 기저가 표현하는 색 공간의 한계를 그대로 따른다. [추정]

## 4. 독립 구현 방침(clean-room)

원칙: 원본의 코드·계수·격자표·안료 상수를 쓰지 않는다. 같은 구조(잠재 색 = 농도 + 잔차, 농도에서 색을 만드는 3차 식, 선형 보간)를 이 저장소의 자체 모델과 자체 데이터로 새로 만든다.

1. 역할 분리: 이 문서를 쓴 쪽(원본을 읽음)과 구현하는 쪽(원본을 읽지 않음)을 나눈다. 구현 쪽은 `node_modules/mixbox`와 `mixbox` 소스 사본을 열지 않는다.
2. 안료 기저: 저장소의 31밴드(400~700nm, 10nm) Kubelka–Munk 구현과 개방 KM 참조 데이터에서 네 안료를 자체로 고른다. 출처와 라이선스를 코드 주석이 아니라 문서에 적는다.
3. 순방향 식: 농도 격자에서 KM 혼합 반사율을 계산해 sRGB로 변환하고, 그 표본에 3차 20항 다항식을 최소제곱으로 적합한다. 계수는 생성 스크립트가 결정적으로 만들고 상수 수십 개로만 저장한다.
4. 역방향: 격자표 데이터 파일을 쓰지 않는다(번들 크기와 청크 수 예산). 농도를 단체(simplex) 위에서 반복 풀이로 구하고, 필요하면 첫 사용 때 작은 시작점 표를 만든다. 모듈을 불러올 때 무거운 계산을 하지 않는다.
5. 잔차: 3.5와 같은 개념으로 무손실 왕복을 보장한다.
6. 혼합: N색 가중 평균. 가중치는 정규화하고 음수·NaN을 거부한다.
7. 라이선스 프로필: 제공자 `toonstudio-latent-pigment-v1`을 권리 `internal`로 등록하고 `permissive-only` 프로필에서 허용한다. Mixbox 자체의 비상업 경계(`mixbox-js-v2`)는 서면 합의 근거가 기록되기 전까지 그대로 둔다.
8. 비교: 개발 전용 스크립트가 있으면 같은 입력 쌍에서 두 결과를 ΔE로 비교해 보고만 한다. 원본의 값을 시험 기대값이나 상수로 쓰지 않는다. 운영 번들에는 포함하지 않는다.

## 5. 검증 계획

- 왕복: 임의 색 → 잠재 → 색에서 8비트 오차 0, 부동소수 오차 1e-9 이하.
- 항등: 단일 색 가중치 1은 같은 색.
- 대칭·연속: 두 색의 교환, 가중치 변화에 대한 연속성, 가중치 합 정규화.
- 안료다운 혼합의 방향성: 파랑+노랑이 선형 RGB 평균보다 초록 쪽, 흰색+빨강이 분홍 쪽으로 간다(방향만 확인하고 값은 고정하지 않는다).
- 결정성: 생성 스크립트를 다시 돌리면 같은 계수가 나온다.
- 성능: 초기화 비용과 초당 변환 수를 측정해 문서에 적는다.
- 번들: 새 청크와 새 정적 데이터 파일이 늘지 않는다(번들 래칫).
