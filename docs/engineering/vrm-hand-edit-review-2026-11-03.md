## 재현과 수정

`studio-vrm-finger-curl-polarity.test.ts`에 추가한 회귀 검사에서 수정 전
`루미/left/1 첫 단독 편집 방향`이 실패했다. 검지만 `+0.6` rad 적용한 결과와
중지를 함께 굽혀 축을 판별한 결과의 검지 회전 차이가 `1.2` rad였다.

`resolveFingerCurlPolarity`는 손가락을 초기화하고 입력 포즈를 적용한 뒤 중지 끝의
손바닥 방향 이동량을 측정했다. 검지·약지·새끼만 편집하면 중지가 움직이지 않아
이동량이 0이고, 루미처럼 축 반전이 필요한 모델에도 기본 극성 `+1`을 반환했다.
캐시 생성 여부와 편집 순서에 따라 같은 입력이 다르게 보일 수 있는 원인이다.

입력 포즈 대신 부호별 고정 크기 `±0.35` rad 중지 시험 회전을 사용한다.
최종 회전 적용·문서 형식·손목 보정·반대손 보존 경로는 기존 코드를 사용한다.
큰 입력각이나 중지 이외 손가락의 단독 편집도 동일한 시험 회전으로 축을 판별한다.

## 편집기 재점검

타입 검사와 분리해 전체 Vite와 Chromium만 실행하자 약 100초 후 실제 캐릭터 셰이퍼가
열렸다. 앞서 본 복구 문구는 `public/offline-draw/bootstrap.js`의 10초 타이머가
React 루트 미마운트를 감지해 표시한 안내다. 그 문구만으로 편집기 실행 실패를 확정할 수 없다.
개발 API 서버(`127.0.0.1:4001`)가 없어 auth/session·capabilities·AI 상태 요청은
502/ECONNREFUSED로 실패했지만 캐릭터 편집과 기기 저장은 동작했다.

실제 셰이퍼의 포즈 → 손 포즈 → 왼손 손가락 하나씩에서 검지 값을
20 → 40 → 15 → 35도로 입력했다. 이어 변형 저장 UI에서 `손가락 회귀 20261103`으로
저장했고 저장 완료 안내를 확인했다. SQLite/OPFS 저장소를 직접 되읽은 결과
`fingerOverrides.leftIndexProximal = [0, 0, -0.6108652381980153]`이었다.
페이지 새로고침 후에도 같은 저장값이 남았다. 화면 증거는 `/tmp/vrm-editor-saved.png`다.
고급 편집 → 연출 → 세부 조정·상태 저장에서 같은 이름의 상태를 눌러 실제 복원도 실행했다.
셰이퍼로 돌아와 검지 입력값이 다시 `35`임을 확인했다.
복원 화면 증거는 `/tmp/vrm-editor-reopened.png`다.

추가 발견: 이 단독 손가락 편집 후에도 셰이퍼의 실행 취소 버튼이 비활성 상태였다.
화면의 변경 슬롯 수도 0이었다. 손가락 축 보정과 별개로 셰이퍼 저작 이력과 호환
손가락 슬라이더의 연동을 추가 조사해야 한다. 이번 작은 축 보정에는 이력 구조 변경을 섞지 않았다.

- `pnpm harness:verify`의 하네스·lint·시크릿·아키텍처·파일 크기·진입 그래프 검사는

  Vite도 함께 종료됐으며, 손 비교 화면만 여는 최소 설정으로 WebGL 검증은 복구했다.
- 다른 서버를 종료하고 `node --max-old-space-size=10000 node_modules/typescript/bin/tsc
  -p tsconfig.json --incremental false`로 같은 루트 타입 검사를 다시 실행했으나
  JavaScript heap out of memory로 종료됐다. API 타입 검사 단계도 실행되지 못했다.
  필수 전체 타입 검사와 pre-push 게이트를 우회하지 않으므로 원격 푸시·PR 생성·main 병합은
  완료하지 않았다. 메모리가 더 큰 클라우드 환경에서 전체 검증 후 이어서 처리해야 한다.
- 루트 tsconfig의 진입 소스는 16,803개(약 176MiB)이며 테스트 7,014개를 포함한다.
  이 환경의 cgroup 메모리 상한은 16GiB다. 검사는 단일 tsc 프로세스로 실행되므로
  테스트 worker 수를 줄이는 것으로 루트 타입 검사 메모리 문제를 해결할 수는 없다.
- 개발 서버·브라우저를 모두 종료하고 실제 pre-push를 Node 힙 13,000MiB로 실행했으나
  타입 검사에서 다시 종료 코드 137이 발생해 푸시는 실행되지 않았다.
  원인 조사에서 메모리 기반 `/tmp`의 pnpm 캐시가 2.7GiB의 shmem을 점유함을 확인했다.
  작업 중 생성한 캐시를 디스크 기반 `/workspace/.cache/toon-pnpm-store`로 옮기고 기존
  캐시 경로에는 심볼릭 링크를 남겼다. `/tmp` 사용량은 2.7GiB에서 24MiB로 줄었다.
  코드·검사·훅은 변경하지 않았으며 캐시 이동 후 같은 pre-push를 다시 검증한다.
