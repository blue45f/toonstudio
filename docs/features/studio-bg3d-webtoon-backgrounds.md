# 3D 배경 웹툰 배경 원클릭 — 교실·복도·거리, 방 만들기 자동 단면, v2 방 빌더 정리

상태: `current` (2026-10-16 기준 구현, 기준 커밋 `37b51837`). 하지 않은 것과 한계는 [8. 알려진 한계와 하지 않은 것](#8-알려진-한계와-하지-않은-것)에 따로 적었다.
실제 브라우저(WebGL) 뷰포트에서 사람이 조작해 확인한 기록은 없다. 이 문서의 동작 설명은 순수 단위 시험, jsdom 컴포넌트 시험,
소스 경계 시험, 실제 호스트 코드를 붙인 시험으로 검증한 범위를 뜻한다. 실행한 명령과 결과는 [7. 검증](#7-검증)에 있다.

## 한 줄 요약

3D 배경 편집기의 템플릿 탭 맨 위에 **교실·복도·거리를 사람 키 기준 실제 크기로 한 번에 만드는 선택기**를 두었다.
결과는 이름 있는 일반 도형이라 만든 뒤에도 벽·책상·가로등을 하나씩 고르고 옮기고 지울 수 있다. 쓰이지 않던
`scene-3d` v2 방 빌더는 **자동 단면 규칙만 v1 방 생성 경로로 옮기고 나머지는 삭제**했다. 자동 단면은 켜고 끄는
토글과 시험까지 갖췄고, 숨긴 벽은 안내와 "숨긴 벽 되돌리기" 버튼으로 한 번에 되살린다. 카메라 연출(S3)에서는 렌즈 시프트 가로·세로 슬라이더, 캡처 비율 4:5·21:9, 시네마틱 디렉터 "컷 비율"과
캡처 프레임의 연결을 마무리했다.

### 1.2 v2 를 어떻게 했나 — 규칙만 옮기고 삭제

선택지는 (a) v2 의 데이터와 자동 단면을 v1 생성 경로에 연결, (b) v2 삭제였다. 둘을 섞었다.

- **v2 가 실제로 가진 것.** `buildParametricRoom` 은 벽 네 개의 위치·크기와 오프닝 목록을 **데이터로만** 돌려주고 메시를 만들지
  않았다. 여섯 "원형(archetype)"(교실 9.0x7.5x3.2m, 옥상, 카페, 오피스, 병실, 알현실)은 치수와 소품 이름 문자열 표이며 어떤 코드도
  읽지 않았다. 복도·거리는 원형에 없다. `evaluateAutoCutawayWalls` 만이 고유한 판정이었다.
- **v1 이 이미 더 구체적이다.** 문·창을 벽에 실제로 뚫고(좌·인방·우 박스 조합) 가구·계단까지 도형으로 만들며, 이미 편집기에 연결돼 있다.
  v2 표를 v1 로 "연결"해도 쓸 데이터가 없었다.
- **그래서.** 자동 단면 판정은 v1 로 옮겨 연결·시험하고(아래 2절), 쓸 곳이 없는 나머지(원형 표·벽 데이터)는 시험과 함께 삭제했다.
  `docs/benchmarks/studio-competitor-replacement-program.json` 의 PR-036 증거 경로와 `docs/reports/shaper-competitive-benchmark-2026-09-12.md`
  표의 경로는 `bg3d/studio-bg3d-room-builder.ts` 로 1:1 교체했다(증거 경로 수 123 유지, 검증 스크립트 통과).
- 삭제 뒤 `check-unconnected-code` 보고에서 v2 `test-only-module` 과 방 만들기 패널 `unmounted-component` 가 사라졌고, 새로 생긴 항목은 없다.

## 2. 방 만들기 자동 단면

방 밖에서 안을 바라보는 카메라는 카메라 쪽 벽에 가려 첫 화면에 바깥 벽만 보인다. 방을 추가할 때 그 벽을 숨길 수 있다.

- **판정(벽마다).** 카메라가 그 벽 바깥쪽에 있고(엄격히 평면 밖) 초점이 카메라보다 안쪽이면 그 벽을 숨긴다. 벽 방향은 룸 빌더 규약을 따른다:
  앞벽(남, +Z)·뒷벽(북, -Z)·왼벽(서, -X)·오른벽(동, +X).
- **높이 조건(v2 에 없던 보강).** 시선이 벽 평면을 지나는 높이가 벽 윗단보다 높으면(옥상 난간 1.1m 를 높은 카메라가 내려다보는 경우) 그 벽은
  시선을 가리지 않으므로 숨기지 않는다. 시선이 정확히 윗단과 같은 높이면 숨긴다.
- **숨김 방식.** 가려지는 벽의 벽체 파츠(오프닝으로 쪼개진 조각 전부)를 `visible: false` 로 만든다. 지우지 않으므로 파츠 수는 같고, 레이어 목록의 눈
  아이콘으로 개별로 다시 켤 수 있다. 숨김은 저장 후 다시 열어도 유지된다(시험). 숨긴 도형이 그려지는지·클릭을 받는지·캡처에 들어가는지는 [2.1](#21-숨긴-도형은-클릭캡처에서-어떻게-되나)에 따로 적었다.
- **한 번만 판정한다.** 추가하는 순간의 카메라(뷰포트 `readView()`, 없으면 문서 카메라)로 한 번 판정하고, 이후 카메라를 옮겨도 다시 계산하지 않는다.
  문서에 "방"이라는 묶음 개념이 없기 때문이다.
- **오프셋 반영.** 기존 도형이 있으면 방이 `기존 도형 수 x 폭/6` 만큼 옆으로 밀리므로, 판정은 밀린 만큼 뺀 방-로컬 좌표로 한다.
  이렇게 두 번째 이후 배경은 첫 배경에서 멀리 떨어진다(교실 99개 뒤에 교실을 만들면 +X 로 148.5m, 거리는 도형 하나당 약 4.3m). 1차 판은 이 이동을 알리지 않아
  새 배경이 화면 밖에 생긴 채 아무 일도 없는 것처럼 보였다. 지금은 안내에 "+X 방향으로 148.5m 떨어진 곳"을 적고 "새로 만든 곳 보기" 버튼을 둔다.
  버튼은 기존 "선택 객체 화면 맞춤"을 그대로 부른다 — 방금 만든 묶음의 첫 도형(바닥)이 이미 선택돼 있기 때문이다. 카메라를 **자동으로 옮기지는 않는다**:
  자동 단면은 실제 카메라로 한 번 판정하므로 판정 뒤에 카메라를 옮기면 숨긴 벽이 새 시점과 어긋난다.
- **기본값.** 스위치("자동 단면 (카메라 쪽 벽 숨김)")는 두 곳에 있고 상태를 **따로** 둔다. 웹툰 배경 선택기는 **켜짐**, 방 만들기 패널은 **꺼짐**이다.
  1차 판은 둘이 한 상태를 공유하고 기본이 켜짐이어서, 예전 "방 추가"를 쓰던 사람이 아무 말 없이 앞벽이 사라진 방을 받았다(독립 검토 지적). 선택기는 교실을
  눌러 바로 안을 보는 용도이고 기본 카메라 `[4,3,6]` 에서 앞벽이 시선을 가리므로 켜 둔다. 방 만들기 패널은 예전 동작을 지키려고 꺼 둔다(켜면 같은 안내가 뜬다).
  꺼 두면 예전과 똑같이 모든 벽을 보이게 추가한다. 두 값은 문서에 저장하지 않는 입력 편의라 편집기를 다시 열면 기본값으로 돌아간다.
- **숨겼을 때의 안내와 되돌리기(두 UI 공통).** 숨긴 벽이 있으면 추가 직후 "시선을 가리는 앞벽 13조각을 숨겼어요…" 안내와 **"숨긴 벽 되돌리기" 버튼**이 뜬다.
  버튼은 방금 만든 묶음에서 숨긴 조각의 id 만 한 번의 상태 교체로 다시 보이게 한다(호스트 `showSceneParts`, 이미 지운 조각은 건너뛴다). 복도 앞벽처럼 오프닝 때문에
  13조각으로 쪼개지고 이름이 모두 같으면("앞벽 벽체") 레이어 목록에서 눈 아이콘을 하나씩 켜기 어렵기 때문이다. 조각 이름을 따로 붙이지는 않았다 — 숨김 여부는 눈 아이콘이
  보여 주고, 이름 표시는 켠 뒤에도 남아 틀린 표시가 된다. 안내와 버튼은 선택기·패널 컴포넌트가 들고 있어서 템플릿 탭을 닫았다 열면 사라진다. 그 뒤에는 눈 아이콘으로 하나씩 켠다.
- **기본 카메라에서 가려지는 벽(시험으로 고정).** 카메라 `[4,3,6]` → `[0,0.6,0]`: 교실 앞벽 / 카페 앞벽·오른벽 / 원룸 앞벽·오른벽 / 복도 앞벽 /
  옥상 없음(난간이 낮아서) / 서재 앞벽·오른벽. 교실에서 오른벽이 빠지는 것은 카메라 X(4)가 벽 평면(4) 위라 엄격히 바깥이 아니기 때문이다.

호스트에서는 합성 오브젝트·방 만들기·웹툰 배경이 쓰는 "도형 묶음 추가"를 하나의 경로(`addGeneratedParts`)로 합쳤다. 노드 수 한도 검사, 한 번의 상태 교체(되돌리기 한 단계),
첫 도형 선택이 모두 같은 곳에서 처리된다. 이 경로는 더한 도형 목록(못 더했으면 `false`)을 돌려주고, 안내는 그 목록에서 숨긴 조각을 센다.

### 2.1 숨긴 도형은 클릭·캡처에서 어떻게 되나

| 경로 | `visible:false` 도형 | 확인한 방법 |
| --- | --- | --- |
| 뷰포트 그리기 | 그려지지 않는다 | 코드 읽기(`BgPrimitiveMesh`·`BgCustomModelMesh` 가 `visible` 을 three 그룹에 옮긴다). 브라우저 렌더로 보지는 않았다 |
| 뷰포트 클릭 선택 | 클릭을 받지 않아 뒤의 보이는 도형이 선택된다 | 시험(`StudioBg3dSceneNodes.hidden-pick.test.tsx`: 실제 컴포넌트를 R3F 에 올리고 포인터 이벤트를 보낸다. 수정을 빼면 3개가 실패하는 것을 확인) |
| 배치·삽입 포인터 | 이미 `visible` 을 거른다 | 코드 읽기만 했다(`StudioBg3dPlacementPointerController`, `studio-bg3d-inference-pointer`) |
| 컷 저장 | 컷이 그 순간의 보임/숨김을 도형마다 기록한다. 숨긴 채 저장한 컷은 적용하면 숨김으로 돌아가므로, 벽을 되살린 뒤 예전 컷을 적용하면 다시 숨겨진다 | 코드 읽기(`captureStudioBg3dShot` 의 `nodeVisibility`) |
| 문서 저장·다시 열기 | 유지된다 | 시험(문서 어댑터 왕복) |
| 캡처(삽입·저장·배치 출력)·다중 패스·Babylon 아티팩트 | 같은 장면을 그리므로 숨긴 도형은 그려지지 않는 것으로 **추정**하지만 렌더 결과로 확인하지 않았다 | 확인 못 함 |
| 매직 마스크 | 편집기 안내문이 "숨겨진 프리미티브나 숨겨진 그룹의 자식은 마스크에 나타나지 않아요"라고 한다 | 안내문을 읽었을 뿐 마스크 생성 코드를 읽거나 돌리지는 않았다 |
| 장면의 외부 내보내기(GLB 등) | 이 편집기에서 장면을 GLB 로 내보내는 경로를 코드 검색(`GLTFExporter`·`exportGlb`)으로 찾지 못했다 | 확인 못 함 |

1차 판에는 숨긴 도형도 클릭을 받는 결함이 있었다. three 의 `Raycaster` 는 `visible` 을 보지 않아서, 숨긴 앞벽이 보이는 책상보다 카메라에 가까우면 책상을 눌러도 벽이 선택됐다
(독립 검토가 재현). 눈 아이콘으로 숨긴 도형도 같은 컴포넌트라 똑같았다. 숨긴 도형은 R3F 이벤트 핸들러를 달지 않도록 고쳤다.

## 3. 원클릭 웹툰 배경

### 3.1 구조

```
사이드바 템플릿 탭(탭이 열렸을 때만, Suspense 안)
  StudioBg3dWebtoonBackgroundPicker  (지연 청크, 자동 단면 기본 켜짐)
     └ 카드 클릭 → onBuild((기존 도형 수, 카메라 뷰) → BgPrimitive[])
          └ 호스트 addGeneratedParts: 한도 확인 → 상태 교체 한 번 → 첫 도형 선택 → 더한 목록을 돌려줌
     카탈로그 studio-bg3d-webtoon-background-templates.ts
        ├ 방(교실·복도): 룸 빌더 스펙 → planStudioBg3dRoomBuild (+ 자동 단면)
        └ 거리: studio-bg3d-street-builder.ts
     StudioBg3dBuildNotice + studio-bg3d-build-notice.ts: 추가 직후 안내, "숨긴 벽 되돌리기"(호스트 showSceneParts),
        "새로 만든 곳 보기"(기존 화면 맞춤). 두 UI 가 같이 쓰는 지연 청크 안의 모듈
  StudioBg3dRoomBuilderPanel (지연 청크, 자동 단면 기본 꺼짐 — 상태는 선택기와 따로)
```

선택기·패널·안내·카탈로그·거리 생성기는 런타임 바인딩에서 `import()` 로만 불러온다. 정적 import 경계는 소스 시험이 고정한다(런타임 바인딩이 이들을 `import()` 로만 가져오고,
제품 코드에서 이들을 정적으로 가져오는 곳이 정해진 파일뿐임). 선택기와 방 만들기 패널은 일반 `lazy` 대신 저장소의 `lazyRetry`(`shared/lib/lazy-retry`)로 감쌌다:
방 만들기 패널은 예전에 정적이어서 청크 로드 실패라는 새 경로가 생겼고, 배포 뒤 옛 청크가 사라진 경우 일반 `lazy` 는 앱 오류 경계가 편집기를 오류 화면으로 바꾼다.
`lazyRetry` 는 새로고침을 한 번 시도하고 그것이 취소되면 편집기를 로딩 상태로 둔다(`chunk-load-recovery.ts` 의 설명). 같은 파일의 기존 지연 패널 셋(씬 템플릿 등)은 그대로 일반 `lazy` 다.
실패를 실제로 만들어 새로고침 복구까지 확인하지는 않았다(소스 시험이 `lazyRetry` 사용과 서로 다른 chunkId 만 고정한다).

### 3.4 만든 뒤에도 개별 편집 가능

- 모든 도형은 고유 id 와 이름(`앞벽 벽체`, `책상 상판`, `가로등 기둥` 등)을 갖고, 잠금·부모·묶음 연결이 없는 평범한 노드다. 도형끼리 배열을 공유하지 않는다(시험).
- 문서 어댑터(`tryAdaptStudioBg3dRuntimeToDocument` → 직렬화 → 파싱 → `hydrateStudioBg3dDocumentToRuntime`)를 거쳐도 도형 수·id·이름·종류·색·위치·크기·회전·보임/숨김이
  그대로다. 문서는 각도를 [-π, π) 로 정규화하므로 룸 빌더가 가구 파츠 회전을 처음부터 그 정규형으로 적는다(yaw 180° 는 π 가 아니라 -π, 방향은 같다 — 8절의 핸드오프 결함 참조).
- 템플릿 정리 패널("추가된 템플릿 정리")의 한 묶음 선택·삭제와는 연동하지 않았다 — 방 만들기 결과와 같은 평범한 노드다.

### 3.5 번들

BG3D 편집기 활성화 번들 기준선(`scripts/bundle-baseline.json`)은 건드리지 않았다. 정적으로 남는 모듈은 늘리지 않으려고 새 UI(선택기·안내)는 모두 지연 로드로 두었고, 약 13KB 인 방 만들기 패널도
지연 로드로 바꿨다. 2차 수정에서 런타임 바인딩이 `shared/lib/lazy-retry`(와 그것이 가져오는 `chunk-load-recovery`)를 정적으로 가져오게 되었다 — 앱 라우터가 이미 쓰는 모듈이라
같은 청크에 있을 것으로 보이나 번들 크기를 측정하지는 못했다(아래 추정치에도 넣지 않았다). 활성화 정적 폐포 안에서 바뀐 모듈(사이드바·런타임 바인딩·호스트·렌즈·캡처 비율·룸 빌더·가구·문서)을 기준 커밋과 현재로 **모듈 단위 최소화(esbuild)해 비교한
근사치는 raw 약 -7.3KB, gzip 약 -1.4KB** 다. 이 환경에서는 `public/assets` 가 없고 메모리 한계로 vite 프로덕션 빌드를 돌릴 수 없어 실제 번들 게이트(`check:studio-bundle`)는
측정하지 못했다. 정적 진입 그래프 래칫(`check-studio-eager-graph`)은 통과한다(creator/bg3d 17/17).

규칙을 더하고 결함 시험을 빠뜨리면 이 시험이 걸린다(작성 시점 57/57, 한 결함 시험을 망가뜨리면 그 시험과 메타 시험이 함께 실패하는 것을 확인). 메타 시험은 id 가 적혀 있는지만
보고, 그 결함이 그 규칙을 실제로 걸리게 하는지는 각 결함 시험이 따로 본다.

## 6. S3 카메라 연출 정리

### 6.1 렌즈 시프트 가로·세로 슬라이더

- "렌즈 · 투영" 구역에 가로·세로 시프트 슬라이더(±2, 0.01 간격), "2점 투시 보정" 버튼, "시프트 초기화"를 두었다(`StudioBg3dLensShiftControls`). 슬라이더는 다른 렌즈 슬라이더와 같이 움직이는 동안 미리보기만 하고
  손을 뗄 때 한 번 커밋한다(실행 취소 한 단계). 예전에는 버튼이 세로 값 하나만 계산해 넣었고 가로 값과 직접 조절은 없었다.
- **값의 의미.** 문서 `camera.lensShift` 는 프레임 한 변의 비율이고(±2), 화면에서 장면 전체를 NDC `(-2·sx, +2·sy)` 만큼 옮긴다: 가로 +는 장면이 왼쪽으로, 세로 +는 위쪽으로 간다.
  **사진 렌즈의 라이즈(렌즈를 위로 올리면 장면이 아래로 내려간다)와 세로 부호가 반대**다. 슬라이더 설명 문구가 이 방향을 그대로 말하고 라이즈와 반대라는 점도 적는다
  (독립 검토가 문구가 방향을 분명히 말하는지 다시 확인하라고 했다 — 방향은 위 시험이 부호까지 고정하고, 라이즈와의 비교는 렌즈 구조에서 따진 것으로 사진기로 확인하지는 않았다).
- **같은 값으로 쓰이는지**(`studio-bg3d-lens-shift-pipeline.test.ts`, 32개): 엄격 직렬화·파싱 왕복과 한도 클램프, 컷 저장·적용, Three 뷰포트(점 투영이 법칙대로 이동, 라이브 카메라에서
  되읽기), 캡처 프레임 크롭(삽입과 저장 캡처가 같은 `applyStudioBg3dCaptureFrameViewOffset` 을 쓴다 — 핀박스·레터박스·세로 비율에서 시프트가 유지되고 해제 뒤 정확히 복원),
  Babylon 투영(NullEngine 으로 계산한 투영 행렬이 Three 와 일치 — **캡처 프레임이 뷰포트 전체일 때만**, 아래 한계 참조), 소실점 가이드(렌더되는 먼 점의 수렴점과 일치).
- **Babylon 투영의 한계(고치지 않음).** Babylon 캡처 카메라는 출력 크기에 맞춰 세로 fov 로 투영을 만들고 시프트를 "출력 프레임 한 변의 비율"로 읽는다. 뷰포트 안전 프레임 크롭은 모른다.
  그래서 뷰포트 비율과 출력 비율이 다르면 Three 삽입 결과와 어긋난다. 1200x800 뷰포트로 잰 값: 같은 비율(3:2)은 일치, **4:5** 는 시프트 0 에서 일치하지만 가로 시프트 0.2 에서 가로 NDC 가 0.35
  어긋나고(세로는 일치), **21:9** 는 시프트 0 에서도 어긋난다. 4:5·21:9 프리셋이 이 차이를 더 자주 드러낸다. 고치려면 뷰포트 크기를 Babylon 캡처 요청까지 실어 보내야 한다(기존 환산 함수
  `resolveStudioBg3dCaptureFrameCameraSettings` 를 쓸 수 있다). 이 한계는 파이프라인 시험이 값과 함께 고정하므로 고치면 그 시험이 먼저 실패한다. 매직 마스크는 시프트가 0 일 때만 만들 수 있어서(편집기가 그렇게 막는다) 시프트 쪽 어긋남은 겪지 않지만,
21:9 처럼 출력이 뷰포트보다 낮을 때의 세로 fov 차이는 시프트 0 에서도 있다(이전부터 있던 차이이며 이번에 새로 생긴 것은 아니다).
- **배치 출력 경로.** 배치는 컷마다 `applyStudioBg3dShot` 으로 문서 카메라(시프트 포함)를 적용하고 `applyStudioBg3dViewToThreeCamera` 로 뷰포트에 반영한 뒤 캡처 어댑터로 출력한다. 시프트 값은 컷 저장·적용
  시험과 뷰포트 적용 시험까지는 고정돼 있다. `shot-batch-plan.ts` 는 시프트를 다루지 않고 출력 비율만 동결한다.

### 6.2 캡처 비율 프리셋

`STUDIO_BG3D_CAPTURE_ASPECT_PRESETS` 에 **세로 4:5(인스타)** 와 **와이드 21:9** 를 더했다. 목록은 뷰포트, 21:9, 16:9, 4:3, 1:1, 4:5, 3:4, 9:16 순서다. 프리셋 순서·이름표·비율 일치와
시네마틱 디렉터 선택지와의 대응을 시험이 고정한다.

문서 캔버스 비율이 고정 프리셋과 같으면(웹툰 캔버스 4:5 가 흔하다) 출력 비율 선택 칸의 "문서 캔버스 비율" 항목을 만들지 않는다. 같은 비율이 두 항목이면 선택 칸이 처음 맞는 항목을
보여 줘서, 사용자가 고른 "세로 4:5" 가 "문서 캔버스 비율" 로 바뀐 것처럼 보였다(독립 검토 지적). 두 항목은 같은 비율 값을 저장하므로 고른 결과는 같다. 이 변화는 16:9·9:16·1:1 같은
기존 비율의 캔버스에도 똑같이 적용된다(그 캔버스에서는 문서 캔버스 항목의 픽셀 크기 표기가 사라진다).

### 6.3 시네마틱 디렉터 "컷 비율"

- **사실.** 이전 "컷 비율"은 북마크의 `panelAspect` 메모일 뿐 캡처 프레임과 이어지지 않았다.
- **연결.** 3D 장면과 연결된 덱(제작 모드)에서는 "컷 비율"이 문서 캡처 프레임 비율(LT 탭의 "출력 비율"과 같은 값, `output.exportAspectRatio`)을 바꾸고 읽는다. 선택지는 자유(뷰포트 비율),
  9:16, 4:5, 1:1, 16:9, 21:9 이고, 현재 문서 비율이 이 다섯에 없으면 "직접 지정"(선택 불가, 표시 전용)이 하나 더 보인다. 리허설 덱처럼 연결되지 않은 곳에서는 라벨이 "컷 비율 (메모)" 이고 안내문이 메모일 뿐이라고 말한다.
- **컷마다 저장하지는 않는다.** 이 값은 문서 전체에 하나뿐이다(배치 출력 계획이 문서 비율 하나를 전제로 한다). 안내문도 그렇게 말한다.
- **연결하다 발견한 기존 결함.** 캡처 비율을 고정한 문서에서는 컷 저장이 항상 실패했다(컷 출력 스냅샷에 문서 공통 비율이 섞여 엄격 정규화가 거부 → `null`, 화면에는 엉뚱하게 저장 한도 오류).
  7개 고정 비율 전부에서 컷 저장·적용·복제·이동·엄격 직렬화 왕복이 되도록 고쳤다.

## 8. 알려진 한계와 하지 않은 것

- **실제 브라우저 확인 없음.** 선택기 클릭, 단면 토글, 숨긴 벽 되돌리기, 생성된 교실·복도·거리의 모양, 레이어 목록에서의 개별 편집을 실제 WebGL 뷰포트에서 눈으로 확인하지 않았다. 생성 결과의 모양은
  도형을 간이 래스터라이저(화가 알고리즘)로 그려 본 눈 확인뿐이다. 숨긴 도형이 클릭을 받지 않는 시험은 WebGL 없이 가짜 렌더러로 R3F 이벤트 경로만 본 것이다.
- **사람 크기 허용 범위는 가정이다.** 법규·표준에서 가져온 값이 아니고 이 저장소가 정한 값이다(4절).
- **문과 창은 구멍이다.** 룸 빌더의 문·창은 벽에 뚫린 구멍이라 문짝·유리·창틀이 없다(거리의 건물 문과 상가 유리는 얇은 박스로 있다).
- **자동 단면은 추가 시점에 한 번만 판정**하고 벽만 숨긴다(천장은 없다). 이후 카메라가 움직여도 다시 판정하지 않는다.
- **안내·버튼의 수명과 대상.** "숨긴 벽 되돌리기"와 "새로 만든 곳 보기"는 선택기·패널 컴포넌트의 상태라 템플릿 탭을 닫으면 사라진다. 그 뒤에는 레이어 목록의 눈 아이콘으로 하나씩 켠다.
  "새로 만든 곳 보기"는 기존 "선택 객체 화면 맞춤"이라 그 사이에 선택을 바꾸면 방금 만든 곳이 아니라 지금 선택한 것을 맞춘다. 두 번째 이후 배경을 만든 뒤 카메라를 자동으로 옮기지는 않는다(2절).
- **고치지 않은 사소한 지적 둘.** (1) 호스트 가방 구조분해에 이제 정의되지 않는 `resetTwoPointPerspective` 가 파일 약 20개에 남아 있다. 이름이 `undefined` 가 될 뿐 해롭지 않고, 20개 파일의 같은 줄을
  건드리면 병렬 브랜치와 합칠 때 충돌만 늘어서 두었다. (2) `instantiateStudioBg3dRoomBuild` 는 이제 제품 호출자가 없고(호스트는 `planStudioBg3dRoomBuild` 를 쓴다) 시험과 런타임 바인딩 재수출에만 남은
  얇은 래퍼다. 단면 없는 계획이 예전 결과와 같다는 것을 비교하는 기준으로 시험이 쓰고 있어 지우지 않았다.
- **선택기 항목은 교실·복도·거리 셋뿐**이다. 카페·원룸·옥상·서재는 방 만들기 프리셋으로 만든다. 거리 길이·층수 등을 바꾸는 UI 는 없다(생성기는 스펙을 받는다).
- **템플릿 정리 패널과 연동하지 않았다.** 한 묶음으로 선택·정렬·삭제하는 기능은 없다.
- **컷마다 캡처 비율 저장은 하지 않았다**(6.3). 문서 공통 값이다.
- **배치 출력의 렌더 어댑터·타일링 경로를 렌즈 시프트와 함께 실제로 돌린 시험은 없다.** Babylon 은 NullEngine 투영 행렬 비교까지이고, 캡처 프레임이 뷰포트 전체가 아닐 때(4:5·21:9 등)
  Three 삽입 결과와 어긋나는 한계가 있다(6.1).
- **`scene-3d/studio-3d-room-building-kit.ts` 의 별도 단면 구현은 그대로 뒀다**(BG3D 생성 경로 밖, 배럴 재수출).
- **프리셋 의자 방향 수정의 hybrid-dcc 영향(1차 판의 설명은 틀렸고 고쳤다).** 1차 판은 "핸드오프는 프리셋 id 와 파츠 수만 본다"고 적었으나 사실이 아니다. 핸드오프는 방 프리셋을
  id 로 다시 생성해 파츠 회전을 문서 노드로 그대로 복사하고, 이어서 엄격 컷 포착(`captureStudioBg3dShot`)을 거친다. 의자 yaw 180° 는 회전이 정확히 π 인데 문서 정규형은 [-π, π) 라
  엄격 정규화가 문서를 거부해 `Could not capture DCC shot` 으로 실패했다(교실 프리셋 핸드오프가 깨졌다). 같은 결함이 수정 전 기준 커밋의 카페·원룸·옥상·서재 프리셋에도 이미 있었다
  (기준 커밋의 룸 빌더로 4건 재현). 1차 판은 이 시험 파일이 환경 매니페스트 부재로 로드되지 않는 상태에서 돌려 보지 못한 채 영향이 작다고 판단했다.
  룸 빌더가 가구 파츠 회전을 문서 정규형으로 적도록 고쳤고(`canonicalStudioBg3dRoomYaw`, 위치는 원래 각도로 돌리고 방향은 같다), 6개 프리셋 모두 핸드오프 시험(프리셋별)과 핸드오프 없는
  직접 컷 포착 시험(`studio-bg3d-room-parts-canonical.test.ts`)으로 고정했다.
- **번들 게이트는 측정하지 못했다**(3.5). `lazyRetry` 의 새로고침 복구도 실패를 만들어 확인하지 않았다(3.1).
