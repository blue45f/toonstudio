# 관리자 통합 작업실

- 상태: **migration — 소스 구현과 검증을 진행하며 운영 적용은 별도 승인 대상**
- 기준일: **2026-11-18**
- 소유 앱: `apps/admin-web`, `apps/api`
- 공유 계약: `packages/contracts/src/admin-workspace/`

## 목적과 진입

`/admin/workspace/`는 사업계획·제출, 클라우드 작업, NestJS 호환성, 의존성·CI,
AI·무료 운영 자료를 함께 관리하는 관리자 화면이다. Web 관리자 운영 화면과 독립 Admin 메뉴에서
전체 문서 탐색으로 연다. 기존 `/admin/platform/quality/`의 CI·QA 검증 보드는 계속 별도로 제공한다.

통합 작업실에서 직접 편집하는 대상은 `coordination`의 통합 검토 기록이다. 각 전문 업무의
상세 편집은 연결된 전문 보드에서 진행한다. 사업계획서의 현재 주장·문서·멘토 반영·제출 후보는
`/admin/growth/business-plan/`에서 관리하며, 통합 작업실의 사업 자료는 권한이 허용된 이전 백업의
읽기 전용 조회다. 두 저장소의 소유자·접근 허용은 각각 관리한다.

Web 빌드는 독립 Admin 번들을 한 번 만들고 각 관리자 경로에 문서 진입점을 조립한다.
자산은 `/admin/platform/quality/assets/`를 공유한다. 앱 소스를 교차 import하거나 CSP의
인라인 스크립트·외부 프레임 허용 범위를 넓히지 않는다. 서비스 워커는 관리자 경로를
오프라인 Web 셸이나 캐시 응답으로 대체하지 않는다.

## 작업과 사실 확인

작업 상태는 `초안`, `검토 필요`, `근거 확인 중`, `보완 완료`, `승인 대기`, `최종 확인`이다.
작업 상태와 별개로 사실 확인 상태, 검증일, 재확인 기한을 표시한다.
출처 링크·원문 위치·기준일·검증자·검증 메모·담당자·담당 작업·다음 조치를 기록한다.

비공개 이전 사업 자료의 호환 계약에는 다음 11개 작업 템플릿이 포함된다. 이는 현재 전문 보드의
편집 상태나 제출 준비 완료를 뜻하지 않는다. 문제 인식, 고객 설득 근거, 제작 공정별 도구 비교, 연결 단절과 병목,
SketchUp·Blender 제공 계획, 매출·벤치마크, 마케팅·통계, 시장·매출 교차검증,
캡처 최신화, 제출 양식, 멘토 반영의 11개 작업을 포함한다. 기본 템플릿에 실제 매출·시장 수치를 넣지 않는다.

- 출처가 없거나 확인되지 않은 수치의 기본값은 `null`이며 화면에는 **미확인**을 표시한다.
- 숫자에는 단위·기간·범위를, 전망에는 산식·가정을 요구한다.
- 시장 규모·전망·비교에는 두 번째 원출처와 독립성을 확인한 메모가 필요하다.
- 동일 출처를 URL 추적 매개변수만 바꾸어 독립 출처로 세지 않는다.
- 주장·수치·원문·SHA 등 검증 대상이 바뀌면 기존 사실 확인을 해제한다.
- 검증 기한이 지난 자료는 재검증 경고를 표시하며 현재 최종 확인으로 집계하지 않는다.
- 코드를 수정하거나 제출·계정 변경·배포하는 요청은 `승인 대기`로만 기록한다. 실행 API는 없다.

통합 검토의 CI 증거는 run·attempt·event·workflow·job·shard와 검사 SHA를 기록한다.
수집 시각과 실제 실행 시작 시각을 구분하고, 같은 실행의 재시도나 더 최신 실패를 이전 성공으로
가리지 않는다. 배포는 실제 적용 시각·SHA·digest와 준비·스모크 결과를 따로 비교한다.
오래된 main 관측이나 서로 모순된 증거는 최종 확인의 근거가 될 수 없다. 화면은 시간 경과와
다시 활성화될 때 유효성을 다시 계산하며 외부 상태를 자동 수집했다고 표시하지 않는다.

저장소와 PR 번호, 원본 보드와 항목 식별자로 같은 변경의 후보를 비교한다. 동등 변경이 main에
포함됐더라도 닫힌 미병합 PR을 병합 완료로 바꾸지 않는다. 승인 상태에는 승인 주체·시각·범위와
관련 증거를 기록하며, 승인 표시가 외부 CI·병합·배포·제출을 실행하지 않는다.

## 문서, 멘토, 제출 점검

이전 자료에 보존된 작업본·제출 후보·문서 이력과 고정 당시의 주장·검증 근거·멘토·점검 목록을 조회한다.
이 화면에서는 문서 편집·제출 후보 고정·멘토 및 점검 항목 갱신을 수행하지 않으며,
현재 자료의 변경은 전문 사업계획서 보드에서 진행한다.
이전 고정본은 이력에 남으며 이후 편집으로 덮어쓸 수 없다.
고정 후 본문·버전·관련 근거가 달라지면 변경 전후와 재고정 필요 상태를 표시한다.

이전 멘토 요청의 원문, 반영 위치, 증거를 함께 조회한다. 보존된 최종 점검은 공식 양식·마감 안내,
수치와 단위, 비교 조건, 캡처, 첨부파일, 개인정보·링크·오탈자, 제출본 일치를 다룬다.
빈 필수 목록, 모든 주장의 제외, 근거 없는 완료 표시는 준비 완료로 간주하지 않는다.
보드의 준비 상태는 실제 외부 제출이나 법적·상업적 사실 확인을 대신하지 않는다.

## 인증과 저장

화면은 `GET /api/admin/me`가 확인한 계정만 전달받는다. 계정·역할 변경에는 화면 상태를 분리하고,
권한이 철회되면 작업 데이터를 제거한다. 서버는 요청마다 활성 계정을 다시 확인한다.

| 경로 | 권한과 동작 |
| --- | --- |
| `GET /api/admin/workspaces/toonstudio?scope=operations` | 활성 `admin`·`operator`가 운영 범위의 저장본·revision·권한을 조회 |
| `GET /api/admin/workspaces/toonstudio?scope=business` | 해당 보관함의 소유자 또는 읽기를 명시적으로 허용받은 계정만 조회 |
| `POST /api/admin/workspaces/toonstudio/save` | `operations`는 활성 `admin`, `business`는 해당 범위의 `canWrite` 권한을 확인해 저장 |
| `GET /api/admin/workspaces/toonstudio/export?scope=…` | 선택한 범위의 현재 `canExport` 권한을 서버에서 다시 확인한 후 반환 |
| `GET/POST /api/admin/workspaces/toonstudio/business-access` | 해당 비공개 보관함 소유자의 접근 허용 조회·변경. 빈 보관함의 명시적 소유권 지정은 별도 조건으로 허용 |

플랫폼 관리자 역할만으로 비공개 사업 자료의 읽기·가져오기·내보내기를 허용하지 않는다.
계정이 비활성화되거나 접근이 회수되면 서버가 거부하며 화면의 자료와 보류 중인 상태를 제거한다.

저장 요청은 `scope`, `expectedRevision`, UUID `mutationId`, `state`를 포함한다. 서버는 범위별
revision과 현재 권한을 확인하고 해당 범위만 병합한다. 운영 범위 저장은 숨겨진 사업 자료나
원문 archive를 삭제하지 않도록 기존 비공개 상태를 보존한다. 공통 계약과 기존 원문·승인 제한·
고정본 보존 조건을 검사하며 기존 세션·CSRF 경계를 그대로 적용한다.
보드 행 잠금과 revision 증가, 감사 기록, 재시도 영수증은 같은 트랜잭션에서 처리한다.

같은 mutation ID와 같은 내용의 재시도는 중복 저장하지 않는다. 다른 관리자가 먼저 저장했다면
409 응답으로 충돌을 알리고 현재 초안을 화면에 보존한다. 통신 실패로 결과를 모를 때는
같은 요청으로 재시도하거나 초안을 백업한 뒤 최신 저장본을 확인한다.
다른 관리자의 데이터를 오래된 초안으로 자동 덮어쓰지 않는다.

이 화면의 저장은 서버 DB를 사용한다. 기존 CI·QA 보드의 사용자별 브라우저 저장 방식은 바뀌지 않는다.
API 응답은 `private, no-store`이며 저장소가 준비되지 않았거나 저장본이 손상되면 503으로 실패한다.
그때 임의로 빈 보드를 생성하거나 기존 내용을 초기화하지 않는다.

## 기존 자료 가져오기

선택한 scope의 쓰기 권한이 있는 계정은 기존 Sites 통합 JSON(`toonstudio-admin-integration`,
schemaVersion 1), 사업계획 JSON, 해당 복구 파일의 검증된 작업 내용을 가져올 수 있다.
현재 작업실 형식의 JSON도 지원한다.
파일을 선택한 후 항목 수와 검증 결과를 검토하고 적용한다. 적용 후에는 인증된 저장 API를 거친다.

일반 작업 자료는 UTF-8 기준 12 MiB 이내여야 한다. 복구 컨테이너는 별도 상한으로 읽되,
원본 복구 문자열을 그대로 서버에 보내지 않고 검증된 작업 자료만 사용한다.
중복 ID, 연결이 끊긴 원문, 잘못된 날짜·URL·SHA, 지원하지 않는 버전은 거부한다.

운영 범위에는 허용된 참조 기록만 저장하며 사업 본문·인용·원문 archive·원본 raw 자료를 포함하지 않는다.
전체 원문과 이전 사업 자료는 소유자 또는 쓰기를 허용받은 담당자가 `business` 범위에 가져온다.
해당 비공개 범위에서 원본 JSON을 archive에 보존하고 각 기록의 원문 ID·출처와 연결한다.
현재 편집과 과거 원문을 구별하며, 가져오기만으로 과거 완료 기록을 현재 사실 확인으로 올리지 않는다.
반복 가져오기는 기존 편집을 덮어쓰지 않는다. 비공개 사업 원문·공유 링크·사용자 백업을
공개 저장소나 정적 번들, 테스트 fixture에 포함하지 않는다.

가져오기는 당시 자료의 보관이며 원본 Sites 또는 전문 보드와의 자동 동기화가 아니다.
비공개 자료의 JSON 백업은 사용자가 선택하고 서버에서 내보내기 권한을 다시 확인한 경우에만 수행한다.

## DB 변경과 운영 반영 경계

`0122_admin_workspace.sql`은 `admin_workspace`, `admin_workspace_audit`,
`admin_workspace_receipt`를 추가한다. 보드의 최초 행은 revision 0과 빈 payload만 갖는다.
원문 자료를 SQL에 넣지 않는다. 재실행은 기존 기록을 보존하며 런타임 역할에는 필요한 최소 권한만 부여한다.
브라우저 역할과 PUBLIC 권한은 차단하고, 감사·영수증은 런타임에서 수정·삭제하지 못하도록 제한한다.

`0127_admin_workspace_access.sql`은 범위별 revision, 비공개 보관함 소유자, 명시적 접근 허용과
접근 감사 기록을 추가한다. 소유자가 없는 기존 비공개 자료는 자동 공개하지 않으며, 빈 보관함의
소유자 지정은 명시적 동작으로만 수행한다.

`apiDatabaseFiles` 원장은 전용 ORM 스키마와 추가형 SQL에 필요한 필수 선언 파일만 반영한다.
DB 접근 로직은 `modules/admin-workspace`에 두며 다른 파일 수 예산·검사 기준을 완화하지 않는다.

이 변경의 병합은 운영 DB 적용이나 배포를 실행하지 않는다. 운영 반영 승인 후 다음 순서로 확인한다.

1. [인프라 지도](../operations/infrastructure-map.md)와 [배포 정책](../../DEPLOY.md)에서 승인 범위·대상 SHA·롤백 대상을 확인한다.
2. 격리 DB 검증 결과와 운영 백업을 확인하고 추가형 migration 및 런타임 권한 적용을 승인한다.
3. 같은 승인 SHA의 API와 정적 Web을 반영하고 관리자·운영자·일반 사용자 권한, 실제 저장·재조회·충돌을 점검한다.
4. 관리자가 원본 자료의 가져오기 미리보기를 검토한 뒤 명시적으로 저장한다.

실패 시 애플리케이션을 이전 승인 버전으로 되돌리고 신규 테이블과 기록은 보존한다.
접근 범위 검증이 없는 이전 API로 되돌려야 한다면 비공개 보관함의 API와 화면 경로를 먼저 비활성화한다.
감사·원문·영수증 삭제는 롤백에 포함하지 않으며 별도 승인과 백업이 필요한 파괴적 작업이다.

## 검증 위치

저장소 루트에서 실행한다. UI 브라우저 검사는 합성 계정·데이터를 사용한다.

```sh
pnpm harness:verify
pnpm validate:architecture
pnpm typecheck:admin
pnpm test:admin
pnpm build:admin
pnpm test:admin:e2e
```

공통 계약 테스트는 `packages/contracts/src/admin-workspace/admin-workspace.test.ts`,
서버 검증은 `apps/api/src/modules/admin-workspace/`에서 관리한다.
실제 PostgreSQL 통합 검사는 저장소의 `test:postgres:integration` 절차로 격리된 테스트 DB에서만 실행하며,
필수 CI의 database 작업에도 연결한다. 운영 DB 연결값으로 테스트하지 않는다.
실행 결과와 미실행 항목은 PR에 기록한다.
