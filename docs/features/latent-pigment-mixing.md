운영 배포 완료를 뜻하지 않는다. 이번 변경의 범위는 다음과 같다.

- **current**: `pigment-mixbox`는 기존 저장 데이터의 노드 식별자로만 보존하고, 실행 제공자는

- **migration**: 과거 `mixbox-js-v2/noncommercial` binding을 담은 재료·authoring은 원본과
  신규 receipt를 분리해 명시적으로 이주한다. Mixbox 안료 binding 외의 provider나 매개변수는
  바꾸지 않으며, 다른 copyleft·private-grant 제공자에는 기존 권리 검사를 계속 적용한다.
- **current**: `mixbox` npm 의존성, 외부 패키지 import와 `mixbox-js-v2` 제공자 매니페스트는
  제거한다. 자체 제공자는 기본 `permissive-only`에서 실행한다. 운영 의존성 감사는 외부
  `mixbox` 패키지 재유입을 거부하며, 실제 빌드 포함 여부는 산출물로 따로 검사한다.

  [검증 보고서](../reports/mixbox-internalization-verification-2026-11-05.md)의 해시 대조로 확인했다.

  10장의 권리 상태는 그대로 유지한다.

자체 CPU 공개 경계 `pigment/latent-pigment-api.ts`는 8비트·부동소수 RGB/RGBA 배열·객체, CSS 색 이름·hex와
`rgb()/rgba()`, 선형 RGB 및 자체 7채널 잠재 색 왕복을 제공한다. `lerp*`의 알파는 RGB와 독립
선형 보간하므로 투명색의 RGB도 혼색에 참여한다. 14장의 기존 GPU `mix_rgba`는 coverage로
색 비율을 가중하므로 알파 계약이 다르다. 자체 7채널 배열은 원본 Mixbox의 잠재 데이터와
교환할 수 없으며, API 모양의 대응을 출력 동일성으로 해석하지 않는다.

공개 `glsl()`·`lutTexture()` 기본값은 자체 Float32 표의 비트를 RGBA8 atlas로 보관하는
`packed-float32`다. WebGL1의 float 확장 없이도 실행하며 농도 양자화·표 해상도 하향은 하지 않는다.
직접 resource를 만드는 경로는 지원 장치의 float 경로를 유지하고, 확장 부재나 자동 float atlas의
폭 초과 시 같은 표의 byte 배치로 전환한다. resource의 실제 `textureEncoding`과 shader를
함께 사용한다. 명시적인 WebGL2 3D 배치는 기존 float32 계약을 유지한다. 비트 저장 검증과 실제
GPU의 산술·출력 오차 검증은 [검증 보고서](../reports/mixbox-internalization-verification-2026-11-05.md)에 구분한다.

이 문서는 색을 "안료 4종의 농도 + 3채널 잔차"로 바꿔 섞는 독립 구현의 **현재 구현(current)**, 근거, 한계, 권리 상태를 나눠 적는다. 구현되지 않은 것을 현재 기능처럼 쓰지 않는다. 설계 근거는 [분석 보고서](../reports/mixbox-working-principle-analysis-2026-10-15.md)(역사 자료)의 구조 설명이며, 이 문서가 구현 이후의 현재 사실을 설명한다.

## 2. 구조

잠재 색은 숫자 7개다.

- `concentrations`: 기준 안료 4종의 농도. 순서는 흰색, 노랑, 파랑, 자홍. 0 이상이고 합이 1이다.
- `residual`: R·G·B 잔차. `입력 색 − 0~1로 자른 다항식 색`이며 자르지 않는다.

```ts
rgbToLatentPigment(rgb01)        // → { concentrations, residual }
latentPigmentToRgb(latent)       // → rgb01
mixLatentPigments([{ latent, weight }, ...])  // → latent
mixRgbPigments([{ rgb, weight }, ...])        // → rgb01
```

RGB는 감마 인코딩된 sRGB(0~1)다. 선형 RGB와 알파는 다루지 않는다(호출자가 변환한다).

### 2.1 농도 → 색 (순방향)

채널마다 네 변수 3차 동차 단항식 20개의 가중합이다(세제곱 4개, 제곱×1차 12개, 서로 다른 셋의 곱 4개). 농도 합이 1이므로 세 변수 3차 다항식 전체를 표현한다. 항 순서는 `pigment/latent-pigment-basis.ts`의 표 하나로 정해지며 생성기와 혼합기가 같은 표를 쓴다. 계수는 상수 60개다.

### 2.2 색 → 농도 (역방향)

격자표 데이터 파일은 없다. 입력 색에 대해 가중 목적함수를 단체 위에서 최소화한다.

1. **시작점 표**: 첫 사용 때 농도 단체를 10분할한 286점의 색을 계산해 둔다(계산량은 다항식 평가 286번).
2. **시작점 선택**: 색이 가장 가까운 점 하나, 그리고 그 점과 농도 공간(L∞)에서 0.3 이상 떨어진 점 중 색이 가장 가까운 점 하나. 색이 가까운 점 둘을 그대로 고르면 이웃이 접힌 면의 같은 국소 최소로 몰려, 색역 안 색 2만 개 중 23개를 정확히 풀지 못했다(9장 5번). 하나만 고르면 160개를 놓쳤다.
3. **풀이**: 활성 집합 Levenberg–Marquardt. 합 1 등식은 차분 좌표로 줄여 풀고, 농도 0 경계의 변수는 라그랑주 승수가 풀어 줄 때만 자유 변수로 되돌린다. 걸음이 1e-6 미만이거나 목적함수 상대 감소가 1e-9 이하이면 멈춘다(최대 40회).
4. **목적함수**: 다항식 값이 0~1 밖이면 기울기 0.1로 누설시킨 값과 입력 색의 차이를 쓴다. 경계(채널 0 또는 1)에 닿는 색에서도 해가 연속이도록 하기 위해서다. 또한 무채색 축 성분 오차에는 0.25를 곱한다. 안료 색역 밖의 색(순검정 등)은 정확히 맞출 수 없는데, 이때 명도를 양보하고 색도를 우선하지 않으면 검정이 청록빛 어두운 색으로 풀린다(가중 없이 풀었을 때 검정의 기저가 (23, 80, 75)였다).
5. **잔차**: `입력 − clamp01(다항식(농도))`. 잠재 → RGB는 `clamp01(clamp01(다항식(농도)) + 잔차)`이므로 같은 농도에서 입력 색이 그대로 돌아온다(무손실).

### 2.3 혼합

농도와 잔차를 가중 평균(선형 보간)한 뒤 위 식으로 색을 만든다. 가중치는 최댓값으로 먼저 나눈 뒤 합 1로 정규화한다(합이 넘치거나 사라지지 않는다). 가중치 0인 색은 풀이하지 않는다. 음수·NaN·무한대 가중치, 빈 목록, 범위 밖 RGB는 거부한다.

## 3. 모델 생성 (재현 방법)

```sh
pnpm run generate:latent-pigment-model   # 생성 파일을 쓴다(같으면 건드리지 않는다)
pnpm run verify:latent-pigment-model     # --check: 최신이 아니면 종료 코드 1
pnpm exec tsx scripts/generate-latent-pigment-model.mts --report   # 요약(파일을 쓰지 않는다)
pnpm exec tsx scripts/generate-latent-pigment-model.mts --sweep    # 설계 변수 비교표
```

생성기는 개발 전용이며 운영 번들에 들어가지 않는다. 난수를 쓰지 않고, 입력은 이 저장소의 코드뿐이다.

1. 합성 기준 안료 4종의 31밴드(400~700nm, 10nm) 반사율 곡선을 정의한다(4장).
2. 농도 단체 격자(20분할, 1771점)의 각 점을 저장소의 Kubelka–Munk 31밴드 파이프라인(`studio-spectral-pigment-mixing-provider.ts`)으로 섞는다. 흰색의 산란 세기를 4, 나머지를 1로 두고, 안료의 효과 가중치는 `농도^1.75 × 산란 세기`로 넣는다. 파이프라인이 돌려주는 `scene-linear-srgb-unbounded`(자르지 않은 선형 sRGB)를 부호를 보존한 sRGB 전달함수로 인코딩해 표본을 만든다.
3. 채널마다 Householder QR로 최소제곱을 푼다. 순수 안료 꼭짓점 표본에는 가중치 50을 주어 네 안료의 색을 앵커로 삼는다. sRGB 색역 밖 표본(원래 값이 0 이하 또는 1 이상)은 다항식이 같은 쪽에 있으면 가중치 0으로 두는 검열 반복 가중 적합으로 처리한다. 표시값은 0~1로 자르기 때문이다. 정규방정식의 조건수 문제를 피했고 릿지는 필요하지 않았다(QR 대각 비 최소/최대 2.8e-2).
4. 계수와 적합 오차를 `latent-pigment-model.generated.ts`에 쓴다. 시각·경로·환경 정보가 없고, 숫자는 유효숫자 12자리로 적는다.

**결정성과 `--check`**: 같은 설정이면 계수가 비트 단위로 같다(시험이 증명). `--check`는 생성기를 다시 돌려 파일과 비교한다. 구조(숫자 외 텍스트)는 정확히 같아야 하고 숫자는 절대 오차 1e-6 안에서 같으면 최신으로 본다. Node 버전에 따라 `Math.exp` 등 수학 함수의 마지막 비트가 달라질 수 있기 때문이다. 시험(`scripts/generate-latent-pigment-model.test.ts`)이 이 모드를 실제 프로세스로 실행한다.

## 4. 기준 안료의 선택: 이유·출처·라이선스

### 4.1 출처와 라이선스

기준 안료 4종의 곡선은 **이 프로젝트가 `scripts/generate-latent-pigment-model.mts`에 직접 작성한 매끄러운 합성 곡선**이다. 외부 측정 데이터, 제3자 안료 표, 제3자 코드에서 가져온 상수는 없다. 라이선스는 프로젝트 라이선스(`Project license`)다.

이 저장소에는 허용 라이선스의 실측 도료 데이터베이스가 없다. 기존 분광 제공자도 "호출자가 준 반사율 곡선만 받고 독점 도료 측정값을 내장하지 않는다"는 정책이라 같은 원칙을 따랐다. 개방 KM 참조(`vendor/open-km.reference.js.txt`)의 안료 상수 파일은 저장소에 없다.

곡선의 이름("티타늄 화이트·카드뮴/한자 옐로·프탈로 블루·퀴나크리돈 마젠타 모양")은 일반 안료 계열의 대략적인 스펙트럼 **모양**을 가리키는 설명이며 상표나 특정 제품을 뜻하지 않는다. 실측값이 아니므로 실제 물감과의 일치를 주장하지 않는다.

### 4.2 곡선 (σ는 로지스틱 함수, 반사율은 [0.003, 1]로 자른다)

| 농도 순서 | 안료 | 산란 세기 | 반사율 R(λ), λ는 nm |
| --- | --- | ---: | --- |
| c0 | 백색 계열 | 4 | `0.97 − 0.12·σ((425−λ)/8)` |
| c1 | 노랑 계열 | 1 | `0.02 + 0.88·σ((λ−506)/9)` |
| c2 | 파랑 계열 | 1 | `0.015 + 0.36·g(λ; 472, 34/30) + 0.06·σ((λ−640)/15)` (g는 좌우 폭이 다른 가우스) |
| c3 | 자홍 계열 | 1 | `0.015 + 0.6·σ((λ−596)/14) + 0.25·σ((450−λ)/26)` |

순수 안료 꼭짓점의 KM 결과 색(0~255, 생성기 `--report`): 흰색 (251, 252, 249), 노랑 (253, 234, 0), 파랑 (0, 76, 151), 자홍 (194, 56, 103).

### 4.3 왜 이 네 가지인가

- **감산 삼원색 + 흰색**: 노랑·파랑·자홍 세 가지로 색상환 대부분을 섞어 만들고, 흰색으로 명도를 올린다. 파랑+노랑이 초록으로, 흰색+자홍이 분홍으로, 노랑+자홍이 주황으로 가는 것이 모델이 나타내야 할 안료 혼합의 대표 방향이다.
- **흰색의 산란 세기 4**: 흰 안료는 착색 안료보다 훨씬 강하게 산란하므로 같은 농도에서 덜 물든다. 값 자체는 자체 결정이다.
- **등량 혼합이 중립이 되도록 곡선을 맞췄다**: 노랑·파랑·자홍을 같은 비율로 섞으면 회색이 나와야 흰색과 검정·회색 사이의 혼합이 색 치우침 없이 이어진다. 파랑 곡선의 장파장 꼬리(`0.06·σ((λ−640)/15)`)를 조정해 맞췄다. 맞추기 전에는 같은 축에서 R이 G·B보다 20단계가량 낮은 청록 치우침이 있었다. 지금은 `--report`가 찍는 4개 지점(흰색 비율 0.85·0.70·0.40·0.00)의 등량 혼합축이 모두 R·G·B 편차 1/255 이하다.
- **반사율 하한을 낮게(0.015~0.02) 두었다**: 하한이 높으면(실험 배율 4) 적합은 쉬워지지만 가장 어두운 혼색이 밝아져 실사용 색까지의 평균 거리가 두 배(22.5 → 47.0)가 된다(5.2장 표).

## 5. 적합 오차와 설계 변수

### 5.1 적합 오차

표시값(0~1로 자른 값) 기준, 1/255 단위. 값은 생성 파일의 `LATENT_PIGMENT_FIT_ERROR`이고 시험이 상한을 지킨다(평균 4, p99 15, 최대 40 미만).

| 표본 | 점 수 | 평균 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| 적합에 쓴 점(20분할) | 1771 | 2.54 | 9.18 | 28.95 |
| 검증(30분할, 적합에 쓰지 않은 점 포함) | 5456 | 2.48 | 9.22 | 28.95 |

최대 오차는 흰색+노랑 변 위 농도 (0.40, 0.60, 0, 0)의 B 채널이다(`--report`). 흰색 모서리 근처에서 KM 반사율이 K/S의 제곱근처럼 급히 변해 3차 다항식이 따라가지 못하는 곳이다. 순수 안료 꼭짓점은 앵커 가중으로 기록된 꼭짓점 색(8비트)과 최대 약 2.0단계(파랑 꼭짓점의 B 채널, 다른 채널은 1.6 이하) 안에서 재현된다. 시험 허용치는 3단계다.

### 5.2 설계 변수 비교 (`--sweep`)

적합 표본 기준, 검증 격자 생략. "실사용 색 거리"는 실사용 색 27개(피부·머리·하늘·잎·빨강 계열 등)에서 다항식이 만드는 색 집합까지의 최근접 거리(1/255)다. 작을수록 그 색이 잔차 없이 표현된다.

| 농도 지수 | 검열 적합 | 하한 배율 | 적합 평균 | p99 | 최대 | 실사용 색 평균 거리 | 최대 거리 |
| ---: | :---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 아니오 | 4 | 2.51 | 14.32 | 32.73 | 49.5 | 173.0 |
| 1.5 | 아니오 | 4 | 1.66 | 5.25 | 14.55 | 47.3 | 171.3 |
| 1 | 예 | 1 | 4.69 | 24.95 | 59.72 | 26.4 | 110.0 |
| 1.5 | 예 | 1 | 2.20 | 9.99 | 31.65 | 23.3 | 111.4 |
| **1.75** | **예** | **1** | **2.54** | **9.18** | **28.95** | **22.5** | **112.4** |
| 2 | 예 | 1 | 3.23 | 10.98 | 20.49 | 22.1 | 113.5 |
| 1.75 | 아니오 | 1 | 2.91 | 11.63 | 18.53 | 22.6 | 112.0 |
| 1.75 | 예 | 4 | 2.28 | 6.65 | 11.88 | 47.0 | 171.1 |

읽는 법과 선택 이유:

- **농도 지수** `p`는 농도 c가 KM 혼합에서 착색 가중치 `c^p`로 들어가게 하는 모델 설계 변수다. p=1(선형)이면 흰색·꼭짓점 근처의 제곱근형 변화 때문에 오차가 크다(최대 59.7). p를 키우면 그 부분이 매끈해져 오차가 줄지만 p=2는 평균 오차가 다시 늘었다. 1.75는 평균과 p99가 가장 균형 잡힌 값이다. 농도는 질량 분율이 아니라 잠재 좌표이므로 이 변수는 물리량이 아니라 적합을 위한 선택이다.
- **하한 배율 4**(밝은 안료)는 적합이 쉬워 보이지만 실사용 색 거리가 두 배(22.5 → 47.0)가 된다. 어두운 색과 진한 색을 표현하지 못한다.
- **검열 적합**은 평균과 p99를 줄이고(2.91/11.63 → 2.54/9.18) 최대 오차는 키운다(18.53 → 28.95). 두 안의 포괄도(22.5 대 22.6)는 같았고, 역방향 풀이 품질(색역 안 정확성, 전수 탐색 대비 최적성, 회색 혼합 중립성, 연속성)도 임시 복사본으로 비교했을 때 거의 같았다(비교 스크립트는 저장소에 남기지 않았다). 표시값 기준 평균·p99를 줄이는 쪽을 택했으며 근소한 차이의 선택이다.
- 위 표 이전에 안료 곡선의 폭·위치·반사율 하한과 자홍의 파랑 영역 로브를 몇 가지 바꿔 본 탐색이 있었고, 그 스크립트는 저장소에 남기지 않았다. 표의 `하한 배율`만 재현 가능한 형태로 남아 있다.

| RGB 큐브 6³ = 216색 | 40.3 | 35.9 | 134.8 | 53 / 216 |
| sRGB 원색 6개 | 91.3 | - | 134.8 | - |

잔차가 큰 실사용 색: `#000000` 74, `#b71c1c` 44, `#202020` 41, `#8e24aa` 37, `#d81b60` 31, `#26a69a` 24. 즉 어두운 색, 진한 빨강·보라·자홍 계열, 순수 sRGB 원색은 4안료 색역 밖이라 잔차가 크고 그만큼 선형 평균에 가깝게 섞인다(한계 9장).

## 6. 성능

`pnpm exec tsx scripts/dev/latent-pigment-report.mts`로 측정했다. 환경: Node v24.21.0(저장소 요구 24.16.0 이상), Intel Xeon(논리 코어 4개). **다른 작업이 동시에 돌던 상태(부하 평균 9~10)**에서 3번 반복한 범위이며, 부하에 따라 실행마다 크게 흔들리는 보수적인 값이다.

| 항목 | 측정값(3회 범위) |
| --- | --- |
| 지연 초기화(새 프로세스 9회 중앙값, 첫 잠재→RGB 호출 − 둘째 호출) | 1.1 ~ 1.8ms |
| 풀이부터 부른 첫 호출(초기화 + 풀이기 JIT + 풀이, 새 프로세스 9회 중앙값) | 3.5 ~ 4.2ms |
| 같은 프로세스의 둘째 풀이 호출 | 0.4 ~ 0.8ms |
| RGB → 잠재 (풀이, 워밍업 후 10만 건) | 21 ~ 40µs/건 (약 2.5만 ~ 4.8만 건/초) |
| 잠재 → RGB | 1.2 ~ 3.8µs/건 |
| 두 색 혼합(풀이 2회 포함) | 50 ~ 72µs/건 (약 1.4만 ~ 2.0만 건/초) |

- 초기화는 모듈을 불러올 때가 아니라 첫 사용 때 한 번 일어난다. 시험이 증명하고, 보고 스크립트도 새 프로세스마다 "불러온 직후에는 미초기화"를 단언한다. 초기화가 하는 일은 계수·항 표 복사, 작업 배열 할당, 286점 시작점 색 계산이며, 그 비용이 위 표의 1.1 ~ 1.8ms다. 첫 풀이는 여기에 풀이기가 처음 실행되는 비용(JIT 워밍업)이 더해져 3.5 ~ 4.2ms다. 초기화 비용은 "첫 잠재→RGB 호출에서 둘째 호출을 뺀 값"으로 근사했으므로 첫 호출에만 드는 다른 비용이 조금 섞여 있을 수 있다.
- 부하가 낮았던 개발 중 측정에서는 풀이가 약 9~15µs/건이었다(Node 버전 미기록, 재현 가능한 기록은 위 보고 스크립트 출력뿐이다).
- 풀이가 한 호출에 수십 µs이므로 획의 매 도장마다 부르기보다 기존 방식대로 색 쌍 하나당 33단계 팔레트를 만들어 캐시하는 경로(`BrushStudioV6MaterialPaletteCache`)에서 쓴다. 팔레트는 풀이 2번과 보간 33번이다.
- 시험은 첫 호출 0.5초, 변환 3000건 3초라는 매우 느슨한 상한만 단언한다.

## 9. 한계

1. **합성 곡선**: 실측 도료가 아니다. 실제 물감과의 색 일치를 주장하지 않는다.
2. **색역**: 안료 4종의 단체로 닿지 않는 색(어두운 색, 진한 빨강·보라·자홍, 순수 sRGB 원색)은 잔차가 크고, 잔차는 선형으로만 섞이므로 그 부분은 안료답지 않다(5.3장).
3. **어두운 색**: 순검정의 기저는 약 (56, 74, 72)로 완전한 무채색이 아니고 가장 어두운 중립 혼색은 (71, 70, 71) 근처다. 검정은 명도 오프셋 잔차(−56, −74, −72 근처)로 담긴다. 회색 쌍 혼합의 최대 채널 편차는 5.6/255다.
4. **다항식 오차**: 최대 28.95/255(흰색+노랑 변). 평균 2.5.
5. **접힌 면**: 다항식의 상이 접혀 있어 같은 색에 농도 해가 여럿일 수 있다. 시작점 2개로 색역 안 색 2만 개 중 1개(오차 5e-4)를 놓쳤다. 입력이 접힘 경계를 넘는 곳에서는 농도가 갑자기 달라질 수 있다. 왕복은 잔차가 보정하므로 안전하지만 다른 색과 섞은 결과는 그 경계에서 달라질 수 있다.
6. **sRGB 경계**: 채널이 0이나 1인 색은 경계로 정규화되어 표시 오차 8e-3(약 2/255) 이내로 풀린다(누설 클램프의 결과).
7. **알파·선형 RGB**: 지원하지 않는다.
8. **성능**: 반복 풀이는 한 호출에 수십 마이크로초이므로 도장마다 부르는 경로에는 쓰지 않는다. 도장마다 섞어야 하는 혼색 브러시는 14장의 표 고속 경로(혼합 1건 약 0.7µs)를 쓴다.
9. **다른 구현과의 차이**: 아래 11장의 참고 수치처럼 보색에 가까운 쌍에서 결과가 크게 다를 수 있다. 어느 쪽이 실제 물감에 가까운지는 판정하지 않았다.

## 14. GPU·표 고속 경로 (2026-10-29)

이 장은 반복 풀이 혼합기를 제품의 캔버스 혼색에 쓸 수 있게 만든 표 고속 경로, 같은 표를 쓰는 WGSL·GLSL ES 3.0 셰이더 모듈, 그 산술의 TS 재현을 설명한다. **검증 상태: Node 에서만 검증했다(구문 해석·산술 재현·단위 시험). 이 컨테이너에는 GPU 가 없어 실기기 GPU 픽셀은 검증하지 않았다.**

### 14.1 표 굽기

- `bakeLatentPigmentTable(N)`이 sRGB 격자 N³ 점마다 반복 풀이(`solveLatentPigmentConcentrationsInto`, 역변환 캐시를 거치지 않는 같은 풀이)를 실행해 농도 4개를 Float32 로 담는다. 같은 N 이면 비트 단위로 같다(시험). 격자점 값은 `rgbToLatentPigment`의 농도를 f32 로 반올림한 값과 정확히 같다.
- 기본 단일 표 `getLatentPigmentTable()`은 모듈을 불러올 때가 아니라 첫 호출 때 한 번 굽는다(시험: 불러온 직후 `isLatentPigmentTableBaked() === false`). 커밋한 데이터 파일은 없다.
- 배치: `concentrations[((b·N + g)·N + r)·4 + k]`(R 이 가장 빠른 축). 그대로 rgba32float 3D 텍스처(x=R, y=G, z=B)로 올린다. N=33 이면 35,937점, 575KB.
- **N=33 을 고른 이유**(2026-10-29 측정, Node v24.22.2, Intel Xeon 2.80GHz 4코어, 부하 평균 0.4~0.7, 고정 시드 임의 색 쌍 3,000개 × 임의 비율, 반복 풀이 혼합 대비 채널 최대 오차, 1/255 단위):

| N | 굽기 시간 | 평균 | p50 | p90 | p99 | 최대 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 17 | 142ms | 0.23 | 0.04 | 0.41 | 4.49 | 14.64 |
| 25 | 267ms | 0.14 | 0.01 | 0.20 | 2.80 | 13.56 |
| **33** | **685ms** | **0.10** | **0.01** | **0.12** | **2.29** | **14.53** |
| 41 | 1,385ms | 0.09 | 0.00 | 0.08 | 1.73 | 13.30 |

  최대 오차는 N 과 거의 무관하다. 다항식 상이 접힌 면(9장 5번)에서 반복 풀이가 고르는 해와 표가 보간한 농도가 다르기 때문이다. p99 는 N=33 에서 2.3/255 로 충분히 작고 굽기 시간은 1초 안이다. 성능 기록 시험(`latent-pigment-table.test.ts`)이 실행마다 굽기 시간을 다시 찍는다(이 작업의 실행: 717ms).

### 14.2 CPU 고속 경로

- 조회: 농도를 표에서 삼선형 보간(x→y→z, `a·(1−t) + b·t`)하고, 잔차는 `입력 − clamp01(다항식(조회 농도))`로 **정확히 다시 계산**한다. 그래서 반복 풀이 모듈의 `latentPigmentToRgb`에 넘기면 입력 색이 그대로 돌아온다(임의 색 2,000개의 왕복 오차 0, 시험 상한 1e-12, 8비트 오차 0). 농도→색 다항식 평가는 반복 풀이 모듈과 항·연산 순서가 같아 비트 단위로 같다(시험).
- 혼합: 농도와 잔차를 가중 평균한 뒤 `clamp01(clamp01(다항식) + 잔차)`. 두 색(`mixRgbLatentPigmentTable`), N색(`mixRgbLatentPigmentsTable`, 가중치 규칙은 `mixRgbPigments`와 같다), 0~255 할당 없는 핫 경로(`mixSrgb8LatentPigmentTableInto`, NaN·범위 밖은 예외 대신 자른다).
- 반복 풀이와의 일치(시험이 지키는 명시 허용치): 고정 시드 600쌍에서 평균 0.5/255, p99 4/255, 최대 20/255 미만. 이 작업의 실행값은 평균 0.090, p50 0.008, p99 3.055, 최대 7.994.
- 연속성: 표 경로는 입력 색에 대해 연속이다. 1/256 간격으로 입력을 움직일 때 출력 변화/입력 변화의 최댓값이 표 경로 1.72, 반복 풀이 15.9 였다(60개 선분 × 256걸음, 개발 중 측정). 시험은 표 경로가 3 미만임을 단언한다.
- 방향성: 노랑+파랑은 선형 RGB 평균보다 초록 쪽, 흰색+빨강은 분홍, 빨강+노랑은 주황 쪽(반복 풀이 시험과 같은 색, 시험).
- 성능(같은 측정 조건): 핫 경로 혼합 약 142만 건/초(0.7µs/건), 검증 API 약 60만 건/초, 반복 풀이 `mixRgbPigments` 약 1.9만 건/초. 시험 실행값: 표 1,399,570건/초, 반복 풀이 17,505건/초. 시험은 느슨한 상한만 단언한다.

### 14.3 셰이더 모듈

`buildLatentPigmentWgsl({ group, binding, tableSize })`와 `buildLatentPigmentGlsl({ tableLayout, samplerName, tableSize })`가 같은 함수 집합을 만든다.

| 함수 | 뜻 |
| --- | --- |
| `latent_pigment_polynomial(c)` | 농도 4개 → 다항식 값(자르기 전). 20항을 항 순서대로 펼친 식 |
| `latent_pigment_table_concentrations(rgb)` | 표 텍셀 8개(textureLoad/texelFetch)의 수동 삼선형 보간 |
| `latent_pigment_from_rgb(rgb)` | 표 농도 + 셰이더 안에서 다시 계산한 잔차(구조체 `LatentPigment`) |
| `latent_pigment_to_rgb(latent)` | `clamp(clamp(다항식) + 잔차)` |
| `latent_pigment_mix_latent(a, b, t)` / `latent_pigment_mix(a, b, t)` | 잠재 공간 보간(감마 인코딩 sRGB 입력) |
| `latent_pigment_mix_rgba(a, b, t)` | 직선 알파. 색 비율은 알파로 가중(`b.a·t / 알파 합`)하고 알파는 선형 보간한다. 투명한 쪽 안료는 섞이지 않는다 |
| `latent_pigment_srgb_to_linear` / `latent_pigment_linear_to_srgb` | 표준 sRGB 전달함수 |
| `latent_pigment_mix_linear(_rgba)` | 선형 sRGB 입력(예: scene-linear 작업면)을 감마 인코딩해 섞고 되돌린다 |

- 계수 주입: 20항 × 3채널 계수를 `latent-pigment-model.generated.ts`에서 읽어 셰이더 리터럴로 펼친다(JS 왕복 표기 그대로, 정수 모양이면 `.0`). 모델을 다시 생성하면 셰이더 문자열도 따라간다. 시험이 각 줄을 다시 읽어 생성 계수와 같음을 확인한다. 생성 문자열은 ASCII 만 쓴다.
- 표: WebGPU 는 `texture_3d<f32>`(rgba32float, 바인드 레이아웃 sampleType `unfilterable-float`, viewDimension `3d`), 업로드 서술은 `latentPigmentWebGpuTableUpload(table)`(bytesPerRow = N·16, rowsPerImage = N). WebGL2 는 RGBA32F `highp sampler3D`(기본) 또는 너비 N·N × 높이 N 의 2D 아틀라스(`packLatentPigmentTableAtlas2d`, 텍셀 (r + b·N, g)). 필터링 없는 형식과 texelFetch 를 쓰므로 하드웨어 필터 정밀도(보통 8비트 분율)에 기대지 않는다.
- GLSL 은 `#version` 줄을 넣지 않고 모든 부동소수 선언에 `highp`를 붙였다(기본 정밀도에 기대지 않는다).

### 14.5 제품 연결: 혼색 브러시

- `brush/studio-wet-mix.ts`의 `mixModel`에 `latent-pigment`를 더했다. 도장마다 `혼색 = 섞는 방식(현재 색, 머금은 색, 혼색율)`의 섞는 방식으로 표 고속 경로를 부른다(스트로크당 버퍼 1개, 도장마다 할당 없음). 혼색율 0 은 현재 색, 1 은 머금은 색이 그대로 나온다(시험: lerp 와 바이트 단위로 같음 / 평평한 바닥 불변).
- 표는 리터치 Worker 안에서 첫 `latent-pigment` 획 때 굽는다(시험: 다른 방식만 쓰면 굽지 않음). Worker 가 유휴 45초 뒤 정리되면 다음 잠재 안료 획에서 다시 굽는다(이 환경에서 약 0.7초, 느린 기기에서는 더 길 수 있다). 기본 실행 경로는 Worker 라 굽기가 화면 스레드를 막지 않는다.
- `StudioWetMixPanel.tsx`에 "섞는 방식" 칩 묶음(네이티브 버튼, `aria-pressed`)을 더했다: RGB 평균(기본, `lerp`) · 분광 물감(`spectral-wgm`) · 잠재 안료(`latent-pigment`) · 빨노파 색상환(`ryb`). 선택된 방식의 설명을 한 줄로 보여 준다. **기본값은 그대로 `lerp`다.**
- 선택은 탭 단위 메모리 상태(`brush/studio-wet-mix-model.ts`)다. 호스트는 획을 Worker 로 보낼 때 이 값을 `mixModel`에 담는다. 반경·혼색율 같은 다른 혼색 설정처럼 문서·브러시에 저장하지 않는다.
- 리터치 Worker 프로토콜은 네 방식을 모두 받는다. 이전에는 코어가 지원하던 `ryb`를 프로토콜이 거부했다(이번에 함께 고쳤다).
- 문지르기(스머지)에는 적용하지 않았다. 스머지는 픽셀마다 RGBA 보간이라 픽셀마다 잠재 안료 혼합을 하면 CPU 비용이 도장당 수천 배로 늘기 때문이다.

### 14.6 한계와 열린 항목

- 셰이더 모듈은 아직 어느 제품 GPU 렌더러도 쓰지 않는다(target). 캔버스 혼색을 GPU 로 옮기려면 목적지를 읽는 혼색 패스(바닥 텍스처 표본화)가 필요하고, 그 패스와 실기기 픽셀 검증은 별도 작업이다.
- 표 근사는 접힌 면 근처에서 반복 풀이와 최대 약 8~15/255 다를 수 있다(14.1·14.2의 최대값). 대신 연속이다.
- GLSL ES 3.0 의 실제 드라이버 컴파일·WebGL2 업로드(RGBA32F 3D 텍스처)는 브라우저에서 확인하지 않았다.
- 브라우저 화면(패널 칩 배치, 터치 크기)과 실제 획의 시각 확인은 별도 UI/UX 단계에서 한다.
- 새 시험 파일(`latent-pigment-table.test.ts`, `latent-pigment-shaders.test.ts`, `brush/studio-wet-mix-latent.test.ts`, `brush/studio-wet-mix-model.test.ts`)은 필수 CI 목록(`scripts/ci-required-vitest-targets.txt`)에 넣지 않았다(13장과 같은 이유). 전체 `pnpm test`에는 포함된다.
